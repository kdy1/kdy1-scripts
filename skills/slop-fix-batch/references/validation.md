# Validation policy

Perform real-world validation for every group whose change has runtime-observable behavior, even when the issue does not request it. Real-world validation exercises the changed behavior in a real target environment: launch the app, CLI, service, or affected tool; reproduce the issue scenario before the change when practical; and confirm the fixed behavior and the acceptance criteria after the change. Capture screenshots or recordings when the behavior is visual. Use the runtime's browser, preview, and device tools when they apply. Automated tests, builds, linters, code inspection, and Git/GitHub state verification remain required. They do not replace real-world validation, even when a test launches the app.

Validate only in local, development, preview, sandbox, simulator, emulator, or test environments. Do not change production data or create outward-facing effects such as messages, payments, or published content. If only production or an unavailable external service can show the behavior, first try every available alternative. If none works, the result is blocked.

Record one `realWorldValidation` result for each group in the ledger, worker handoffs, PR bodies, and final report:

- `passed`: the change was exercised at the exact covered SHA. Record `sha`, `environment`, the steps or commands and the observed result in `evidence`, and paths to logs, screenshots, or recordings when they exist.
- `not-applicable`: the change has no runtime-observable behavior, for example documentation, comments, or test-only changes. Record the concrete `reason`. Build, CI, packaging, and tooling changes are observable: run the affected tool.

A failed validation means the group is incomplete. Fix it in the same worker or report the blocker. A blocked validation (missing environment, credentials, device, service, or data) stops publication of that group and its dependents. The worker reports the concrete missing requirement and every alternative it tried. The coordinator asks the human for that specific access, then resumes validation. Never record a blocked, failed, or skipped validation as `passed`, and never publish a group without a `passed` or `not-applicable` result.

For implementation and PR publication, assess completion against the implementation requirements, passing implementation-worker checks, and the real-world validation result. There is no cumulative-tip or final-tip validation stage. Run required automated checks, including whole-repository checks required for the assigned change, and real-world validation in the implementation worker before handoff. Do not defer them to integration. Preserve Git hooks. If integration changes code through conflict resolution or adaptation, run the checks needed to cover that change before publication and dependent implementation. If the change can affect the validated behavior, repeat the real-world validation at the integration SHA. Record their exact SHA. An unchanged cherry-pick does not require a second validation pass. Report worker coverage at its original SHA; never claim it validated another tip. Use a standalone `Closes` line for each issue completed by the group and `Refs` for intermediate split issues.

Ledgers recorded before this policy may contain `realWorldValidation: "not-performed"` on existing layers. Keep those records honest in reports. Do not use them for a new layer or publication: before an unpublished legacy layer is published, perform real-world validation and record the layer again.

The same evidence standard applies to directly closing already-resolved issues. Use existing evidence or perform real-world validation at the current target SHA for required release or environment acceptance. If neither establishes acceptance, leave the issue open.
