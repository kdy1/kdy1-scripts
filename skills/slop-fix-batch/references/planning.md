# Plan Mode investigation and handoff

When the human invokes this workflow in Plan Mode, complete its investigation in that mode before returning an implementation plan. Apply the read-only parts of **Preflight and fixed selection** and **Assess and group**: resolve the repository and selection conditions, collect the complete canonical fixed list, and record the exact target SHA inspected. Missing or ambiguous conditions require an answer before searching. Failed, capped, partial, or incomplete collection remains a collection blocker; do not dispatch from a truncated list. An empty complete result ends planning with that result.

Use read-only investigation subagents and the [investigation assignment](worker-prompts.md#investigation-assignment), passing Plan Mode explicitly. Use the investigation role settings and keep the shared API budget, concurrency accounting, and validation policy. Inspect every selected issue's body, complete discussion, relevant code and history, and existing fixing PRs. Collect results as they arrive and continue independent investigations, but recover every assignment's result and reconcile coverage of the entire fixed list before finalizing the plan. Do not defer investigation to execution or return only a generic description of this workflow.

For every issue, establish its classification, acceptance requirements, evidence, and proposed fix or reason no new implementation is needed. Reconcile overlaps and confirm actionable groups, directed dependencies, stack membership, implementation approach, and automated validation commands under the existing grouping rules. Ask for material product decisions that the issue and repository cannot resolve. Access failures or missing evidence remain explicit investigation blockers; do not describe the affected investigation as complete or finalize a decision-complete plan while required investigation or decisions remain outstanding.

Plan Mode permits investigation only. Do not implement, close issues, post comments, publish PRs, mutate source or Git refs, create construction worktrees, run stack mutations, acquire construction ownership, start maintenance or register automation, or merge. Use permitted read-only access to the target revision instead of executing mutation steps from preflight; report unavailable revision access as a blocker. Construction ledger fields and registrations belong to execution. Preserve permitted planning observations outside tracked source or in this chat without fabricating execution records. Rules that dispatch implementation while investigation continues, refill publication/repair lanes, or run maintenance checkpoints apply only in execution mode.

Return the final plan in a `<proposed_plan>` block. Include the original conditions, exact query, canonical issue list, repository/base and inspected SHA, per-issue classification and evidence, acceptance requirements, proposed changes, group-to-stack assignments, directed prerequisites, scheduling rationale, validation commands, and known blockers. Distinguish inspection and executed checks from planned checks and skipped real-world validation. Report existing fixing PRs without planning duplicates, and propose evidence-backed closure of already-resolved issues without closing them. Plan dependency constraints and scheduling rules, not a fixed total integration order; actual layer order still follows the existing dependency and completion policy.

After leaving Plan Mode, reuse the fixed list and completed investigation results. Revalidate the target SHA, issue/PR state, changed code, and evidence relevant to the planned groups before implementation or closure. Reconcile affected assessments and dependencies when those facts changed; do not repeat all completed investigations or collect later issues. Initialize the execution ledger from the planning observations and apply the normal preflight, ownership, implementation, publication, and maintenance gates. Planning observations do not satisfy execution-time checks or authorize writes while Plan Mode remains active.
