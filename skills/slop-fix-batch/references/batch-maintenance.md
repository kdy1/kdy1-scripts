# Batch PR maintenance and merging

The slop-fix-batch coordinator owns this procedure directly. Use its [procedure helpers](helpers.md) for maintenance checkpoints and heartbeat continuations. Route authenticated remote requests through its `github-request.mjs`; direct CLI calls remain explicitly unintercepted and must honor recorded cooldowns and invalidation. The same recorded coordinator applies all `batch-ledger.mjs` events. Use checkpoint enqueue/start/finish/invalidate/candidate events and `batch-checkpoints.mjs plan` for pass capture, coalescing and due reads. New events during a pass remain pending. Capture exact PR membership and preserve incomplete observations. Render scoped maintenance/repair-context handoffs with the recorded helper/state paths and capacity; repair START still follows repair-pr's ownership gates. Record fresh stack outcomes through `stack-observation`, keeping publication heads and worker coverage historical. No helper candidate or ledger transition authorizes repair or merging; all gates below remain required. Resume uses ledger validation and explicit recovery rather than missing-state defaults.

Use this procedure only for the exact batch authorized by a human's explicit `$slop-fix-batch` invocation. Skill editing or a ledger path without its human authorization is insufficient. Repository-mode default-branch/author filters and indefinite lifetime do not apply here. Do not change any existing repository-mode watch or its heartbeat to batch mode.

Read the [scheduling and timing](scheduling.md) reference and use its helper for deterministic queue suggestions and coordinator-owned timing transitions. Include CI/review waits, repairs/alignment, merge request and verified result in remaining-path estimates. There is no construction cumulative-tip or final-tip validation stage; retain worker checks, necessary checks for integration changes and the existing current-head CI/review merge gates. Then read [$repair-pr](../../repair-pr/SKILL.md), its [shared coordination reference](../../repair-pr/references/stack-coordination.md), and [$manage-stacked-prs](../../manage-stacked-prs/SKILL.md). Retain the batch's validation policy for delegated repairs: skip manual app launches, real-environment reproduction, and validation screenshots; run required automated checks and disclose skipped validation. Preserve the repair comment policy. Also read [$merge-pr](../../merge-pr/SKILL.md). The original batch invocation authorizes this coordinator to conditionally merge complete passing stacks under **Merge complete stacks** below. Repair subagents never merge or enable auto-merge. Only the coordinator may enable auto-merge for a completed standalone PR under **Standalone auto-merge**; multi-PR stacks use the native whole-stack merge procedure with a verified unsupported-capability sequential fallback. Editing these skills does not merge live PRs, update saved automations, or expand an older watch's authorization; an older repair-only watch requires explicit human merge authorization before its record and heartbeat gain this policy.

Apply `$repair-pr`'s **Comment policy** to the coordinator and every repair subagent. Report progress and outcomes in Codex chats; do not post routine PR comments or reviews by default. Optional English explanations of objectively incorrect bot findings in their original inline threads are permitted, and those threads must be resolved under `$repair-pr`'s finish rules even if a reply is omitted or fails. Preserve any explicit human comment request and its scope in the watch record, heartbeat, and scoped subagent handoff; a batch invocation alone does not request PR comments.

## Establish the batch watch

1. Recover the original human invocation, batch ID, durable absolute ledger path, host/repository, repository checkout, push remote, coordination root, stack IDs and catalog IDs, ordered layers/PR URLs, ready/publication evidence, and construction owners. Verify the recorded publication against authenticated GitHub and confirm the clean integration checkout was detached at its verified tip; do not adopt existing fixing PRs that the batch only reported. The complete target set is every recorded published PR from this batch, including upper layers. Do not filter by author or default base and do not search for additional PRs. A PR remains in the ledger after closure/merge or base retargeting; never create a replacement PR for it.
2. Verify the repository checkout and absolute `repair-pr` skill/helper paths, its `manage-stacked-prs` dependency, `merge-pr`, squash merging with `--match-head-commit`, shared common-directory root, authenticated GitHub access, and scheduling/subagent/worktree tools as in slop-fix-batch preflight, including automation_update, collaboration.spawn_agent, send_message, list_agents, wait_agent, followup_task, interrupt_agent, and isolated Git worktree support. Record native-stack capabilities using **Native whole-stack merge** below; this is read-only capability discovery, never a test merge. Repairs use `collaboration.spawn_agent` with `model: "gpt-6-luna"`, `reasoning_effort: "xhigh"`, and `fork_turns: "none"`. Follow **Dispatch a one-shot repair** below; pass the batch authorization, validation/comment scope, and coordination record. Do not substitute a model, reasoning effort, standalone automation, sidebar chat, or local repair. The common directory must match in every repair worktree.
3. Keep one maintenance record in the existing batch ledger and this coordinating chat. Add mode `batch`, implementation-ended flag, automation ID/state and uncertain outcomes, cadence, exact batch PR identities/order, original authorization and comment scope, attempt history/spawn outcomes/actual agent IDs/task names/worktrees/start handoffs, ownership/reservation/claimed tokens, final heads/alignment and thread outcomes, result-capture and ownership-reconciliation state, skipped validation, and blockers. Retain merge authorization, original complete layer count and standalone eligibility, batch-owned auto-merge request state/attempts/cancellations, each stack's assigned-group completion, gate evidence tied to exact head/base SHAs, effective review requests/thread IDs, current check/run IDs and required-check expectations, merge owner/token, selected merge path and capability evidence, top PR and intended full membership/head/base snapshot, asynchronous request UUID/status, attempts and queue/uncertain outcomes, per-PR merge commit SHAs, pre-merge inherited boundaries, server-side alignment observations, and any local post-merge alignment/validation results. Record pending/active checkpoint events, the pass identity and captured PR set, inventory completeness and per-PR read times, and invalidated observations. The same coordinating owner serializes batch-ledger writes for construction and maintenance; workers return results instead of editing that ledger. Atomic helper state owns locks; the ledger owns human authorization and creation/repair history. Reconcile both on every continuation.
4. Discover existing automations through the tool's documented mechanism (`$CODEX_HOME/automations/*/automation.toml`) and match batch ID, this chat, repository, and ledger. Reuse the matching heartbeat. If another chat owns it, report that owner instead of registering a competing heartbeat. Reconcile overlapping repository watches, repair subagents, and legacy repair chats before assignment; use the shared whole-stack reservation so only one owner can dispatch. Do not widen an existing general watch's query to include the batch.
5. Register the first heartbeat when the first stack has passed complete publication verification and the helper's `ready` transition. Subsequent ready handoffs update the same ledger and watch; no new heartbeat is created. Follow **Adaptive batch cadence** below; preserve explicit human intervals and reuse the existing heartbeat. There is no default total concurrency cap. Share the explicit human limit and runtime capacity with all active/reserved investigation, preparation, implementation, publication, nested, and repair workers. Follow slop-fix-batch's **Shared slots for publication and repair** allocations, lending and reclaim rules. The publication ceiling and repair allocation divide the total budget; they do not add slots. Reconcile lane usage and loans with construction before dispatch, retaining uncertain starts. At safe boundaries collect results and process eligible merges, then allocate repairs before publication and remaining implementation slots under slop-fix-batch’s progress-exception rules; do not wait for other workers, publishers, or CI/reviews. Preserve at most one preparing/running repair per stack. Distinct ready stacks dispatch in parallel.
6. Use `automation_update` to create/reuse one heartbeat in this coordinating chat with the saved prompt below, filling all placeholders. Preserve notification preferences and unrelated fields. Record and reconcile the actual registration result before dispatch. A creation failure leaves publication intact and maintenance reported inactive/uncertain; retry only after reconciling whether registration occurred. Immediately perform one bounded scan after successful registration, then return to implementation without waiting for repair completion.

Local maintenance requires the computer and Codex app to remain running. If no PRs were published, do not register a heartbeat. An interrupted or held stack remains construction-protected and is reported as a blocker; its visible partial PRs do not authorize repairs.

## Adaptive batch cadence

Keep an explicitly human-specified interval unchanged. For a new batch watch without one, use a one-minute heartbeat while any ready stack has pending CI, a pending merge/queue request, uncertain remote effects, or active repair/alignment. Use five minutes when all remaining work is waiting on external review/action or protected construction and no such active state remains. Update the same heartbeat only when this activity class changes; preserve its ID, notification policy, prompt, and unrelated fields, and record the requested and applied cadence. For existing watches, preserve their recorded interval unless the human explicitly authorizes this adaptive policy; loading the revised skill alone does not migrate them.

Use only intervals supported by the automation tool. If one minute is unsupported, record the limitation and use its shortest supported interval up to five minutes; if no such interval is supported, retain the existing supported interval and report the latency limitation. Do not silently round an explicit human interval, create another schedule, or use a shell polling loop. Shared API cooldowns still apply. A faster heartbeat refreshes only due affected stacks; keep the full-inventory interval separate. Checkpoints and delivered completion results trigger immediate bounded work at safe boundaries regardless of cadence.

## Construction checkpoints

After at least one verified ready handoff, record a pending checkpoint for group publication or stack ready handoff, implementation-result collection, verified repair-result collection or descendant-alignment completion, completed group integration or integration-change check completion, and immediately before implementation returns its final report. The final checkpoint follows the ledger's `implementationEnded: true` update. Coalesce pending events at the next coordinator safe boundary into one **Each bounded batch pass**. The registration scan counts as the first handoff's pass. Do not start a full CI/review inventory for every individual PR publication or wait for all active publishers to finish. Construction dispatches publishable groups promptly; maintenance may process other ready stacks while those publishers run. These calls reuse this batch's ledger, coordinator, and single heartbeat. Apply Adaptive batch cadence to the same heartbeat; do not register another schedule or wait for the next tick.

Honor a stopped watch. Reconcile inactive/uncertain registration through **Establish the batch watch** before assignments or merges. Persist the pass identity and checkpoint events it consumes at start. Events and new publication results arriving during that pass remain pending for the next pass at a safe boundary; do not restart the inventory or start a competing pass. Construction calls after releasing its catalog token and reconciling its current Git/gh-stack operation, while retaining building/held stack protection. Publishers on other stacks may remain active. Collect their results, process eligible merge outcomes/candidates, and allocate repairs before publication and remaining implementation slots under slop-fix-batch’s progress-exception rules at safe boundaries within maintenance. Keep catalog mutations serialized with construction, holding that token through each whole command and outcome reconciliation even when it performs network I/O. Checkpoint passes use all normal ownership, fresh-read, recovery, and whole-stack gates. They never wait for CI/reviews or all repairs to finish. Scheduled passes continue after implementation ends under the same termination rules.

Verified repair-result collection and completed descendant alignment also trigger a checkpoint after implementation ends. Mark the affected stack due immediately and refresh its targeted merge gates at the next safe boundary. Agent messages/results may wake the coordinator; otherwise the saved heartbeat collects them. Release or reconcile repair ownership before merge selection. Coalesce events into the next immediate bounded pass at a safe boundary after the active pass ends; events recorded after a pass starts remain pending for that next pass. Do not restart the active inventory, wait for the scheduled tick, or require a full inventory for the affected stack.

## Inventory scope and candidate queue

Capture the recorded PR set at pass start and record the inspected subset separately. Perform complete authenticated inventories at registration, when recovering missing coverage, at a recorded periodic full-scan interval, and before final termination accounting. Between full scans, refresh new publications, changed or invalidated observations, and due pending or unknown results. Choose and record the full-scan interval and next refresh times without changing the heartbeat cadence. Publication checks remain limited to the affected prefix. Use grouped requests or bounded parallel read chunks and fetch every page needed for each inspected PR's checks, reviews, comments, threads, and policy. Record identity, exact head/base SHAs, read time, autoMergeRequest and queue state, check/run attempts, gate state, source inventory, and completeness. Missing or failed pages remain unknown; an incremental pass is not a complete batch inventory.

Keep a separate durable merge-candidate queue. Add a complete ready stack only when complete observations indicate that every remaining open layer passes its gates at the recorded heads and base chain. For an originally standalone stack, use the **Standalone auto-merge** eligibility gates, which permit pending CI after review passes. Record this candidate type explicitly; a multi-PR stack with one remaining open layer is not standalone. Use the queue to select targeted whole-stack checks promptly at safe boundaries, without waiting for another full inventory or heartbeat. Historical candidates may survive a pass as scheduling hints only. Expire gate evidence at pass end; unchanged head/base SHAs never prove that checks, reviews, or policy stayed unchanged. Remove or suspend candidates after a verified blocker, changed head or membership, terminal state, ownership conflict, or unfinished alignment. Unknown or changing mergeability permits a later bounded targeted check, never a merge or a repair by itself. Continue other candidates rather than polling that stack.

Invalidate affected gate observations on a push, repair, replay, retarget, merge, changed membership, head/base, check attempt, review/thread state, or required-check policy. Refresh affected PRs and descendants rather than rescanning unrelated stacks. A base update may affect many stacks; mark their evidence stale and check each selected candidate against its current base immediately before merging. Repair dispatch still requires its immediate fresh signal/ownership read. Merge authorization always requires new complete reads of every remaining open PR under the whole-stack edit token, regardless of queue hints or prior selection evidence.

Reuse fresh observations only within their pass for status accounting and assignment decisions. A new published PR enters the next pending pass; it does not invalidate complete coverage of the captured set. Mark helper `plan` inventory complete only for the exact ledger PR set it evaluates. Partial refreshes or historical hints cannot supply `complete: true`. An incomplete batch-wide plan blocks assignments from that plan, not independently verified targeted repair selection below. Require current complete terminal states for the full ledger PR set before ending the watch.

### Targeted repair selection between full inventories

Keep a durable repair-candidate queue alongside the merge queue. Add ready stacks with observed conflict, relevant unresolved review feedback, or current-head CI failure; preserve source/read times and incomplete observations separately. Queue entries are scheduling hints. Pending CI, missing approval, or unknown mergeability alone is not a repair signal. New publications on another stack must not postpone a repair whose own scope can be fully verified.

For a selected stack, recover its authorization, verified ready handoff, complete registered membership, prior attempts, and active/reserved/uncertain owners. Refresh every member PR's current state, head repository/branch/SHA, base chain, mergeability, current-head latest checks/attempts, and paginated relevant reviews/comments/threads. Reconcile identity changes during reads. Require complete observations for this stack and successful exact-PR and head-repository/branch helper lookups. A building/held stack, missing member data, an unknown lower-layer signal, conflicting ownership, or unfinished alignment defers that stack.

Select the lowest open member with a verified repair signal; do not skip a blocked lower repair to mutate an upper member. Immediately recheck its signal, identity and owners, then use the normal whole-stack `acquire --mode reserved` and two-phase child handoff. Record selection mode `targeted-stack`, its complete inspected PR set and evidence, while retaining batch inventory completeness independently. Do not pass this subset as a complete batch `plan`, bypass reservation/START, or weaken merge gates. After a repair, refresh affected descendants before selecting more same-stack work. Full inventories and the helper's complete plan remain required for batch-wide planning and final termination accounting.

## Each bounded batch pass

At every safe boundary reconcile prior merge/auto-merge effects and process eligible merge candidates first, then allocate eligible `repair-pr` work, publication, and new implementation in that order, applying slop-fix-batch’s single-slot progress exception after two consecutive repair-displaced allocation boundaries. Preserve explicit capacity limits and within-queue priorities. Do not interrupt active workers or wait for blocked/pending candidates. Reapply this order after result collection and before each new assignment; targeted repair selection also follows it.

1. Honor an explicit watch stop before any repair assignment or merge. Record stopped state, disable and verify every pending auto-merge request owned by this batch under **Standalone auto-merge**, deactivate the recorded heartbeat, reconcile already submitted native requests and batch-owned queue entries under Native whole-stack merge’s stop rules, and collect already-finished results without starting new repairs or merges. Report uncertain deactivation. Stopping maintenance does not imply cancellation of running repairs or deletion of construction locks. Only an explicit human resume restarts a stopped watch.
2. Recover the ledger and helper `status`. Reconcile build owners, preparing/running/uncertain creations, reservations and claimed tokens, catalog recovery, prior pushes, thread outcomes, merge attempts/queue outcomes, post-merge alignment, and other managers. Reconcile an earlier merge against authenticated PR state before any new attempt; never repeat a confirmed merge. Reuse shared result collection, corrected retry, and comment rules. Keep incomplete, failed, ambiguous and externally blocked repairs recorded; do not call an idle or inaccessible agent complete.
3. Reconcile newly recorded ready handoffs with complete remote publication evidence. Update the same batch PR set from the ledger; this is inclusion of that batch's own outputs, not an issue rescan or authorization to adopt other PRs. Only stacks whose helper phase is `ready` can be assigned. Early group publication leaves a stack building/held until every assigned group is complete; do not repair or merge its published prefix. Do not alter building or held stacks. A registry transaction/error or missing authorization/ledger data defers assignment instead of creating a fresh run.
4. Select a periodic full inventory or the due incremental subset under **Inventory scope and candidate queue**. Include partial publications solely for status/termination accounting and record which PRs were actually inspected. Include open/closed/merged state, exact head repository/branch/SHA, current base branch/SHA, mergeability, current-head checks and latest attempts, autoMergeRequest and queue state, and paginated relevant reviews/comments. Batch or parallelize independent reads and reconcile head/base changes during reads. Missing data is not a healthy result. Use this reference’s repair-signal assessment; pending checks, missing approval, or unknown mergeability alone do not trigger repair. Do not run the repository-mode default-branch filter in scanning, recovery, or dispatch.
5. Validate actual stack membership and current base chain, including GitHub retargeting after a parent merged. A legitimate base change does not exclude the recorded PR. Reconcile unfinished post-merge alignment under its recorded merge owner/token and pre-merge snapshot before evaluating fresh merge gates; do not acquire a second token or require passing CI before finishing that already authorized alignment. First verify any GitHub server-side alignment against the saved membership, boundaries and intended layer diffs. Accept verified completed alignment without replaying it locally; invoke `manage-stacked-prs` only for verified remaining alignment work. Native merge requests still pending/queued/uncertain prohibit local replay. Uncertain ancestry or concurrent membership changes block that stack rather than authorize a guessed replay. Closed/merged PRs receive no new repair and are never rewritten. Preserve original records; the stack's remaining open upper layers remain eligible when their current boundaries can be verified.
6. Collect bounded `collaboration.list_agents` snapshots and delivered agent messages/results under this reference’s Collect results rules, including its unavailable-handle reconciliation on later heartbeats. Record target repairs separately from upper-only alignment, final remote heads, covered checks, push/review-thread outcomes, and ownership. Require alignment verification, not only a target push. Refresh head/base/check/review signals after a lower repair; discard obsolete upper signals. Do not assign another same-stack repair until ownership/effects are reconciled. Mark that affected stack due immediately and record a repair-result/alignment checkpoint. Continue other free stacks without waiting for all children.
7. First reconcile every batch-owned pending/uncertain auto-merge request, including requests removed from the candidate queue by a new blocker; perform required cancellation before repair selection. Update and drain the merge-candidate queue under **Merge complete stacks**, using fresh targeted whole-stack gates after result collection. Consider every ready stack over the recorded scan cadence; historical hints never establish a pass. Do not stop after the first processed stack. Pending CI/reviews, active repairs, contention, or a failed/queued/uncertain merge defer only that stack; continue other free ready stacks in this pass. The helper's complete `plan` supports batch-wide repair selection and terminal accounting; targeted selection can dispatch fully verified individual ready stacks. Neither establishes merge readiness. Include pending/uncertain merges and unfinished alignment in active-stack accounting.
8. Refresh observations invalidated by result collection, merge, or cancellation before repair selection; if refresh is incomplete, do not label a global inventory complete. For a complete batch inventory, prepare the coordination helper's `plan` using these fresh reads, the implementation-ended flag, and all preparing/running/uncertain active stack IDs; require `complete: true` for assignments from that plan. Between full inventories, use **Targeted repair selection between full inventories** with complete fresh observations of each selected stack. Do not fill missing global plan rows with historical hints. Select the lowest open PR with a verified repair signal in each free ready stack; reuse prior-attempt evidence to avoid repeating an already handled problem and to correct an incomplete attempt. If a lower signaled repair is blocked, do not skip it to mutate an upper layer; continue other stacks. External-log or missing-decision blockers remain associated with that stack, not a retry loop.
9. Immediately before dispatch, re-read the PR's open state, head/base, signal, stack and owners. Reserve the whole stack with `acquire --mode reserved` and persist the attempt/token. Follow this reference’s worktree preparation and two-phase subagent start: spawn read-only preparation, record actual agent identity/worktree in the batch ledger and stack snapshot, then send the scoped start message. The child verifies assignment before claiming its reservation. Keep uncertain spawns/start deliveries reserved; release only after definite rejection or a confirmed stopped child with reconciled effects. Never assign two children to one reservation.
10. Re-evaluate termination using current complete terminal PR states for the full ledger PR set, including any publication recorded after pass start. End automatically only when the ledger says implementation ended, every published PR is closed/merged, and no active/uncertain publications, preparing/running/uncertain repairs, pending/uncertain merges, unfinished alignment, pending checkpoints, or unreconciled/incomplete stack ownership remains. Record completion and deactivate this batch's heartbeat; verify the tool result. An implementation still running, missing inventory, empty interim PR list, healthy open PRs, or an interrupted build is not completion. Report incomplete construction or unresolved ownership requiring action; never release it to make shutdown succeed.

One pass never waits for CI/reviews to settle or repeatedly retries the same failed command. Reuse **Recover incomplete repairs** below: a remaining verified repair signal may justify a new attempt after reconciling the previous effects and correcting the failure cause. This permission applies only to the fixed batch PR set. Report failures and required action, and stay quiet while state is unchanged or non-actionable.

## Repair signals and prior attempts

- For every inspected batch PR, read its current open/closed state, `baseRefName`, head and base SHAs, mergeability, checks, and all relevant review threads and comments, following pagination. Tie checks to the current head and latest relevant run attempt. Ignore superseded runs and previous-head failures. Reconcile a head or base change during inspection before using the evidence. Inspect structured check results even when `gh pr checks` exits nonzero for failing or pending checks; distinguish those results from authentication, transport, or parsing failures. Missing required data defers that PR; it is not a healthy result.
- A repair signal is a confirmed merge conflict (`mergeStateStatus: DIRTY` or `mergeable: CONFLICTING`), a current failing CI check, or an unresolved, non-outdated review thread containing `chatgpt-codex-connector[bot]` feedback. Recognize the equivalent bot login without the `[bot]` suffix when returned by GitHub. Let `$repair-pr` assess whether feedback is actionable, incorrect, duplicate, or blocked. Resolved/outdated threads, approvals, human-only feedback, pending checks, missing approval, and unknown mergeability alone do not trigger repair. An unrelated pending check or unknown mergeability does not suppress another verified signal. External checks without accessible logs remain report-only under `$repair-pr`; retain that blocker rather than dispatching it repeatedly.
- Before selecting a stack PR, look up its exact PR and head repository/branch in the shared coordination helper. A building stack, any reservation/repair/edit token, a registry transaction, or uncertain ownership defers assignment. Reconcile other watches and preparing subagents as well as the helper state.
- Healthy PRs receive no repair subagent. Merged or closed PRs receive no new repair, even if they were previously queued. Skip a PR owned by another preparing/running repair or ongoing maintenance automation, including ownership recorded outside this watch. Serialize PRs sharing a head repository/branch or checkout. Retain and report ownership or unsafe-workspace blockers rather than bypassing them.
- Compare signals with all prior attempts, including the final head and handled findings from a completed repair. Requeue after success only for a new problem or relevant changed evidence, such as a new review on the same head, a new current-head failing run, or a newly confirmed conflict. A timestamp change, a repair's own push, lingering old checks, or agent completion alone does not justify another run. When an attempt failed or ended before handling its assigned signal, apply **Recover incomplete repairs** even if the head and signal are unchanged. Reconcile uncertain side effects and workspace ownership before any retry.

## Recover incomplete repairs

- Verify recorded batch membership and ready-stack eligibility in **Dispatch a one-shot repair** before spawning or resuming a recovery subagent. A remaining signal does not authorize repairs to building/held stacks or unrelated PRs.
- Separate an unsuccessful attempt from a PR that requires an external prerequisite. A skipped merge conflict, wrong skill, exhausted review quota, missing approval, premature no-op, failed local validation, or agent execution error does not remove the PR from the repair queue. Reconcile the finished attempt, confirm the remaining current signal, and continue repair automatically within the original scope.
- Read the previous result and relevant commands. Verify which commits and pushes actually reached the PR, whether review-thread mutations succeeded, and whether a subagent, legacy chat, process, or automation still owns the branch. Preserve completed repairs and attempt history. Resolve uncertain creation, push, or mutation outcomes before creating replacement work; never run overlapping repairs.
- Correct the cause before retrying. For skill-discovery or workflow errors, expose and verify the actual `$repair-pr` installation. For a recoverable tool or environment failure, verify or repair the prerequisite. For code or validation failures, retain the concrete failure evidence and choose a corrective diagnostic or repair approach. Do not repeat an identical attempt without addressing its failure cause. Dispatch at most one new attempt for that PR in a bounded scan; reassess it on the next heartbeat instead of looping within the pass. This is not a concurrency cap across independent PRs.
- Once prior effects and ownership are reconciled, reuse a reachable stopped subagent with `collaboration.followup_task` or spawn a replacement at the required model/settings under the original repair authorization. Pass the corrected approach and current assigned worktree/ownership in the handoff. Do not send follow-ups to legacy sidebar chats or create replacement chats. A fresh attempt uses the two-phase start below. If the prior owner is inaccessible or possibly still running, defer until it is confirmed stopped and its effects are reconciled.
- Require human action only for a concrete missing decision or authority that the original repair scope does not supply, unavailable credentials or access, or unresolved effects or user-owned changes that cannot be safely reconciled. Record the exact prerequisite and the evidence for it. Continue scanning that PR and retry when the prerequisite is available. An inaccessible external-check log remains report-only; a repeated identical external failure does not justify repeated dispatch. Missing review credits or a thumbs-up never gate conflict or CI repair.

## Dispatch a one-shot repair

1. Immediately before spawning or resuming a repair subagent, read the PR's current open state, head/base, signals, complete recorded stack membership, and owners. Require a verified ready batch stack, not a repository default-branch or author match; missing reads defer assignment.
2. For every batch PR, verify registered published membership and reserve its whole ready stack under the shared coordination reference before spawning. Record the attempt, authorization pointer, and reservation token in the batch ledger and registered stack snapshot. Never reserve a building stack. Leave uncertain reservations protected; release only after a definite rejected spawn or confirmed stopped child with reconciled effects.
3. Prepare a separate clean Git worktree serially in the recorded repository, using available worktree tools/conventions. Unless the human supplied a starting Git state, use a detached checkout at the freshly verified PR head SHA; `$repair-pr` owns the exact PR checkout after start authorization. Fetch the exact verified head through the appropriate remote if it is not available locally. Record its absolute path/SHA and verify the same Git common-directory root as the coordinator. Do not steal a checked-out branch, reuse user-owned changes, or substitute a separate clone.
4. Mark the attempt `preparing` with a unique task name containing the run label, PR number, and attempt number. Call `collaboration.spawn_agent` with `model: "gpt-6-luna"`, `reasoning_effort: "xhigh"`, and `fork_turns: "none"`. Count preparing/running agents across the actual runtime tree when applying user/runtime limits; queue overflow without imposing another default cap.
5. The spawn message supplies the scoped handoff below and explicitly permits only read-only preparation until a start message arrives. Record the returned agent ID/canonical task name, worktree, and spawn outcome before any start message or subsequent spawn. Also persist that identity in the registered stack snapshot and batch ledger before START. A failed or uncertain spawn/start delivery must be reconciled before retrying; never create a duplicate to bypass a pending outcome.
6. Record the exact start authorization, then send `collaboration.send_message` to that recorded agent authorizing its attempt to start. If read-only preparation has already finished and the agent is idle, use `collaboration.followup_task` to deliver that same start handoff and trigger its next turn. Record delivery outcome immediately; reconcile uncertain delivery before retrying. Include its actual identity, assigned path, original authorization, and the recorded handoff/snapshot pointer (with reservation owner/token for stacks). The agent verifies its identity and assignment, then claims the reservation before checkout or writes.
7. Let `$repair-pr` own the one-shot workflow. The child uses only its assigned worktree, does not register automations, create sidebar chats, or merge PRs, and returns actual covered SHAs/checks, commits/pushes, review-thread outcomes, affected upper-layer alignment, remaining tokens, and blockers.

### Repair subagent handoff

Supply resolved values, not literal placeholders:

- Exact PR URL and absolute installed `$repair-pr` skill/helper paths; instruct the child to read the skill before repair.
- Assigned absolute worktree path, starting SHA, repository/host, and common-directory root.
- Original human batch authorization, exact scope, explicit comment instructions/scope or none, and the batch validation constraints.
- Current repair signals and, for recovery, previous verified effects, failure cause, and corrected approach.
- Attempt/task name, coordinator identity and record pointer; coordination ID, snapshot/ledger path, reservation owner/token, and expected membership.
- Read-only preparation until the coordinator records the actual agent identity and sends the start handoff; then verify assignment before claiming ownership or mutating.
- Return results to this coordinator through agent messages/final output; preserve uncertain ownership and worktrees.

## Collect results

- Read delivered subagent messages/final outputs and use `collaboration.list_agents` for bounded status snapshots. Use `wait_agent` only when useful, with waits at most 60 seconds; it announces updates rather than returning their content. Do not poll unchanged state or require all repairs to finish in one heartbeat.
- Capture and verify each result before recording completion: exact commits/final heads, actual checks and covered SHAs, handled signals, push/review-thread outcomes, upper-layer alignment, blockers, uncertain effects, and remaining owners/tokens. An idle agent, no-op claim, or missing final output is not completion while its assigned repairable signal remains. A target push alone does not finish a stale stack. Pending follow-up CI is monitored by the next scan; do not claim pre-push checks cover new heads.
- On heartbeat continuation or runtime restart, reconcile recorded identities with available agent status/messages. If a handle is unavailable, preserve the attempt and inspect its worktree, pending Git/catalog operations, execution ownership, and authenticated remote outcomes. Absence from the current agent tree does not prove it stopped or released ownership. Require positive evidence that the prior owner stopped and effects are reconciled before transferring tokens or assigning replacement work. Use the shared recovery procedure for retained stack locks; if evidence is unavailable, report the blocker and continue other assignments.

## Merge complete stacks

The maintenance coordinator owns this procedure. Do not wait for other stacks or the batch-wide `implementationEnded` flag. Process every eligible stack in each checkpoint or scheduled pass. Reconcile an unknown setup attempt before retry or deciding ownership. Pending state consumes no worker slot and does not block other stacks or implementation. On verified merge, record its commit, release reconciled ownership, and invalidate base observations for unstarted independent stacks. No descendant alignment is needed for a standalone PR.

If reviews cease to pass, identity/head/base changes, CI fails, repair becomes necessary, or the human stops the watch, disable a pending batch-owned auto-merge with `gh pr merge <PR_URL> --disable-auto` under its recorded token and freshly verify PR state and `autoMergeRequest`. ### Whole-stack gates

These are the full gates for multi-PR stacks and standalone fallback merges. Standalone auto-merge uses the shared review rule here with its explicitly relaxed pending-CI gate above.
