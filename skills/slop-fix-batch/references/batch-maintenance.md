# Batch PR maintenance and merging

In delegated mode, a recorded maintenance actor owns this procedure for its one ready stack; the coordinator owns global allocation, direct management, refresh deadlines, stop/resume state and final batch accounting. An inventory actor separately owns one captured global read pass. In a legacy ledger the coordinator retains maintenance execution. Read [delegation](delegation.md) and [helpers](helpers.md). Actors submit only granted events via batch-ledger submit; ordinary repair workers return facts. Use the shared github-request helper, complete paginated reads, checkpoint coalescing and fresh stack-observation outcomes. Candidates and ledger transitions do not authorize mutations. Recover actual grants/owners and unknown effects before replacement. In the procedures below, **maintenance owner** means the granted ready-stack actor, or the coordinator in legacy mode. It consumes a real slot in delegated mode.

Use this procedure only for the exact batch authorized by a human's explicit `$slop-fix-batch` invocation. Skill editing or a ledger path without its human authorization is insufficient. Repository-mode default-branch/author filters and indefinite lifetime do not apply here. Do not change any existing repository-mode watch or its heartbeat to batch mode.

The coordinator uses [scheduling and timing](scheduling.md) for global queues and timing records; actors read only the assigned capacity/timing requirements and submit scoped outcomes. Include CI/review waits, repairs/alignment, merge request and verified result in remaining-path estimates. There is no construction cumulative-tip or final-tip validation stage; retain worker checks, necessary checks for integration changes and the existing current-head CI/review merge gates. Load [$repair-pr](../../repair-pr/SKILL.md) and its [shared coordination reference](../../repair-pr/references/stack-coordination.md) before repair dispatch, [$merge-pr](../../merge-pr/SKILL.md) before merging, and [$manage-stacked-prs](../../manage-stacked-prs/SKILL.md) only for proven alignment work. Reuse previously read unchanged references. Retain the batch validation and repair-comment policies for delegated repairs. The original batch invocation authorizes the maintenance owner to conditionally merge complete passing stacks, or their passing lower prefix below a confirmed conflict, under **Merge complete stacks** below. Repair subagents never merge or enable auto-merge. Only the maintenance owner may enable auto-merge for a completed standalone PR under **Standalone auto-merge**; multi-PR stacks use the native whole-stack merge procedure with a verified unsupported-capability sequential fallback. Editing these skills does not merge live PRs, update saved automations, or expand an older watch's authorization; an older repair-only watch requires explicit human merge authorization before its record gains this policy.

Apply `$repair-pr`'s **Comment policy** to the maintenance owner and every repair subagent. Report progress and outcomes in the coordinator/worker conversations; do not post routine PR comments or reviews by default. Optional English explanations of objectively incorrect bot findings in their original inline threads are permitted, and those threads must be resolved under `$repair-pr`'s finish rules even if a reply is omitted or fails. Preserve any explicit human comment request and its scope in the maintenance record and scoped subagent handoff; a batch invocation alone does not request PR comments.

Verified merging of implemented PRs is the primary objective. At each new-assignment safe boundary, check ready stacks for due gates, merges and result verification before additional implementation. Targeted work does not wait for a full inventory, other worker results or a delayed refresh. CI/review waits alone permit independent construction with available slots. Merge priority does not relax any ownership, membership, review or CI gate.

## Establish direct batch management

1. Recover the original human invocation, batch ID, durable absolute ledger path, host/repository, repository checkout, push remote, coordination root, stack IDs and catalog IDs, ordered layers/PR URLs, ready/publication evidence, and construction owners. Verify the recorded publication against authenticated GitHub; confirm clean detachment at its verified tip for ready handoff or before building-prefix repair; do not adopt existing fixing PRs that the batch only reported. The complete target set is every recorded published PR from this batch, including upper layers and corrective PRs recorded under **Recover target-branch CI**. Do not filter by author or default base and do not search for additional PRs. A PR remains in the ledger after closure/merge or base retargeting; never create a replacement PR for it. A corrective PR for a new post-merge regression is a separate recovery output, not a replacement or a new fixed-list issue.
2. Verify the repository checkout and absolute `repair-pr` skill/helper paths, its `manage-stacked-prs` dependency, `merge-pr`, squash merging with `--match-head-commit`, shared common-directory root, authenticated GitHub access, and scheduling/subagent/worktree tools as in slop-fix-batch preflight, using the selected [runtime tool mapping](runtimes.md), including creation, messaging/resume, result/stop evidence, bounded waits, and isolated Git worktree support. Record native-stack capabilities using **Native whole-stack merge** below; this is read-only capability discovery, never a test merge. Repairs use the runtime creation tool with the fields returned by `worker-settings.mjs repair --runtime <runtime>`. Follow **Dispatch a one-shot repair** below; pass the batch authorization, validation/comment scope, and coordination record. Do not substitute a model, reasoning effort, standalone automation, sidebar chat, or local repair. The common directory must match in every repair worktree.
3. Keep one maintenance record in the existing batch ledger and this coordinating chat. Add mode `batch`, implementation-ended flag, `management: direct`, state `active`/`stopped`/`completed`, refresh deadlines, exact batch PR identities/order, original authorization and comment scope, attempt history/spawn outcomes/actual agent IDs/task names/worktrees/start handoffs, ownership/reservation/claimed tokens, final heads/alignment and thread outcomes, result-capture and ownership-reconciliation state, skipped validation, and blockers. Retain merge authorization, original complete layer count and standalone eligibility, batch-owned auto-merge request state/attempts/cancellations, each stack's assigned-group completion, gate evidence tied to exact head/base SHAs, effective review requests/thread IDs, current check/run IDs and required-check expectations, merge owner/token, selected merge path and capability evidence, top PR, selected merge prefix and excluded conflict boundary when applicable, and full membership/head/base snapshot, asynchronous request UUID/status, attempts and queue/uncertain outcomes, per-PR merge commit SHAs, pre-merge inherited boundaries, server-side alignment observations, and any local post-merge alignment/validation results. Record pending/active checkpoint events, the pass identity and captured PR set, inventory completeness and per-PR read times, and invalidated observations. The helper serializes ledger writes; granted execution actors submit only scoped events while the coordinator owns global policy/allocations/management state. Atomic helper state owns locks; the ledger owns human authorization and creation/repair history. Reconcile both on every continuation.
4. Reconcile overlapping repository watches, repair subagents and legacy repair chats before assignment; use the shared whole-stack reservation so only one owner can dispatch.
5. Start direct management when the first prefix has passed publication verification. Building-prefix repair dispatch belongs to the coordinator; ready-stack gate/merge jobs still require the helper’s `ready` transition. Subsequent publications and ready handoffs update the same ledger. No automation registration or scheduled continuation is needed. There is no default total concurrency cap. Share the explicit human limit and runtime capacity with all active/reserved investigation, preparation, implementation, publication, nested, and repair workers. Follow slop-fix-batch's **Shared slots for publication and repair** allocations, lending and reclaim rules. The publication ceiling and repair allocation divide the total budget; they do not add slots. Reconcile lane usage and loans with construction before dispatch, retaining uncertain starts. At safe boundaries collect scoped results; allocate due targeted maintenance gate/merge jobs, then confirmed merge-blocking repairs, other repairs, publication and remaining implementation slots under slop-fix-batch’s progress-exception rules; do not wait for other workers, publishers, or CI/reviews. Preserve at most one preparing/running repair per stack. Distinct ready stacks dispatch in parallel.
6. Record active direct management in the maintenance event without an automation ID. Allocate one bounded initial inventory job and independently eligible ready-stack jobs; continue construction without waiting for those jobs or repair completion. Recover the original authorization, ledger/helper/state paths, actual concurrency, validation/comment scope and delegated versus legacy mode from the ledger on every continuation.

An interrupted or held stack remains protected until owners and effects are reconciled. Resume held construction to `building` before using the published-prefix repair handoff; visible PRs alone are insufficient authority.

## Direct management loop and waits

At each safe boundary collect delivered worker results and reconcile known effects, then use `batch-coordinator.mjs observe` to collect changed local status, due checkpoints, ready-stack candidates, capacity and cooldowns in one call. Process the due gate/merge/result jobs and refill independent work under the scheduler. Remote observations still come from the existing inventory/maintenance jobs; local summary completeness never replaces their coverage or fresh gates. Repeat in this same active coordinator execution through construction, repair and verified terminal accounting. Never return merely because PRs were published, implementation ended, or external CI/review remains pending. Bounded actors return their slots after known results; the coordinator stays available to collect results and dispatch the next job.

When no independent work is eligible, use the returned `waitMs` with an interruptible runtime wait of at most 30 seconds. A zero duration means process due work before waiting. After context compaction or interruption call `batch-coordinator.mjs resume` and read its authorization/context and effect references before continuing. Use the selected runtime’s result notifications and bounded waits from [runtime tools](runtimes.md). Cap each wait at the earliest relevant refresh/full-inventory deadline and re-evaluate on new input or agent results. A wakeup is not permission for another API read: refresh only due affected stacks, honor recorded human intervals and shared API cooldowns, and keep full inventories separate. For new batches without explicit intervals, set targeted refreshes one minute ahead for pending CI/merge/queue outcomes and five minutes ahead for external review/action; use a five-minute full-inventory interval. Results and invalidations mark affected stacks due immediately; cooldowns still apply. Do not repeatedly read unchanged remote state, create schedules, or launch shell/background polling loops.

A wait timeout alone is not a new allocation boundary or a state transition. If no result, invalidation, due deadline, assignment or policy change occurred, wait again without writing scheduler/timing/ledger events or re-rendering handoffs. A due pass still records its actual read completion and next deadline even when remote content is unchanged. Reuse complete observations within that pass and report only changed status/blockers with observation paths; do not echo unchanged responses. Preserve all fresh pre-merge gates, uncertainty reconciliation and pagination requirements.

End management only after verified terminal accounting, an explicit human stop, required human input, or an unrecoverable blocker after available independent work is exhausted. Include recorded target-branch recovery work and its corrective PRs in terminal accounting even when all original issue PRs have merged. Report blocked or closed-unmerged outcomes honestly. Before yielding for input or a blocker, preserve attempts, deadlines, ownership and remaining work in the ledger; do not fabricate completion or release uncertain tokens. Runtime interruption is not completion. On an explicit continuation recover this same batch, reconcile owners and remote effects, then resume due work without recollecting issues or repeating uncertain writes. Only an explicit human resume overrides a recorded stop.

## Construction checkpoints

After at least one verified prefix publication, record a pending checkpoint for group publication or stack ready handoff, implementation-result collection, verified repair-result collection or descendant-alignment completion, completed group integration or integration-change check completion, and immediately before implementation returns its final report. The final checkpoint follows the ledger's `implementationEnded: true` update. Coalesce pending events into one captured inventory pass; allocate targeted ready-stack maintenance independently at the next coordinator safe boundary. The initial inventory counts as the first handoff's pass. Do not start a full CI/review inventory for every individual PR publication or wait for all active publishers to finish. Construction dispatches publishable groups promptly; maintenance may process other ready stacks while those publishers run. These jobs reuse this batch's ledger with their recorded grants. Collect and schedule them directly without a delayed refresh or scheduled continuation.

Honor stopped management state. Recover authorization and ownership through **Establish direct batch management** before assignments or merges. Persist the pass identity and checkpoint events it consumes at start. Events and new publication results arriving during that pass remain pending for the next pass at a safe boundary; do not restart the inventory or start a competing pass. A stack executor records its checkpoint at a known safe boundary after releasing its catalog token and reconciling its operation. Other ready-stack jobs need not wait for that executor or a global scan; retain building/held protection. Publishers on other stacks may remain active. Collect their results, process eligible merge outcomes/candidates, and allocate confirmed merge-blocking repairs, other repairs, publication and remaining implementation slots under slop-fix-batch’s progress-exception rules at safe boundaries within maintenance. Keep catalog mutations serialized with construction, holding that token through each whole command and outcome reconciliation even when it performs network I/O. Checkpoint passes use all normal ownership, fresh-read, recovery, and whole-stack gates. They never wait for CI/reviews or all repairs to finish. Direct management passes continue after implementation ends under the same termination rules.

Verified repair-result collection and completed descendant alignment also trigger a checkpoint after implementation ends. Mark the affected stack due immediately and refresh its targeted merge gates at the next safe boundary. The coordinator collects delivered agent messages/results during the direct loop and its short interruptible waits. Release or reconcile repair ownership before merge selection. Coalesce events into the next immediate bounded pass at a safe boundary after the active pass ends; events recorded after a pass starts remain pending for that next pass. Do not restart the active inventory, wait for a refresh deadline, or require a full inventory for the affected stack.

## Inventory scope and candidate queue

Capture the recorded PR set at pass start and record the inspected subset separately. Perform complete authenticated inventories at direct management start, when recovering missing coverage, at a recorded periodic full-scan interval, and before final termination accounting. Between full scans, refresh new publications, changed or invalidated observations, and due pending or unknown results. Choose and record the full-scan interval and next refresh times independently of the short coordinator waits. Publication checks remain limited to the affected prefix. Use grouped requests or bounded parallel read chunks and fetch every page needed for each inspected PR's checks, reviews, comments, threads, and policy. Record identity, exact head/base SHAs, read time, autoMergeRequest and queue state, check/run attempts, gate state, source inventory, and completeness. Missing or failed pages remain unknown; an incremental pass is not a complete batch inventory.

Keep a separate durable merge-candidate queue. Add a complete ready stack when complete observations indicate that every remaining open layer passes its gates at the recorded heads and base chain, or that **Merge below a confirmed conflict** has a nonempty passing lower prefix. Record the conflict and selected prefix separately from the full stack membership. For an originally standalone stack, use the **Standalone auto-merge** eligibility gates, which permit pending CI after review passes. Record this candidate type explicitly; a multi-PR stack with one remaining open layer is not standalone. Use the queue to select targeted whole-stack checks promptly at safe boundaries, without waiting for another full inventory or refresh deadline. Historical candidates may survive a pass as scheduling hints only. Expire gate evidence at pass end; unchanged head/base SHAs never prove that checks, reviews, or policy stayed unchanged. Remove or suspend candidates after a verified blocker in the selected merge range, changed head or membership, terminal state, ownership conflict, or unfinished alignment. Unknown or changing mergeability permits a later bounded targeted check, never a merge or a repair by itself. Continue other candidates rather than polling that stack.

Select the candidate with the highest `mergeablePrCount` first, using existing priorities only for ties. Record the count from complete observations under [scheduling's count rules](scheduling.md#mergeable-pr-count): all remaining open PRs in a passing whole stack, or only the permitted passing lower prefix below a confirmed conflict. Already-merged PRs and pending-CI auto-merge candidates do not count. Pass the count to both legacy merge tasks and delegated maintenance tasks. Update it after changed observations and set it to zero when evidence becomes stale or incomplete; a missing count also means zero. Reapply this order at each new selection after result collection. Preserve pending-effect recovery and fresh pre-merge gates; the count never authorizes a merge.

Invalidate affected gate observations on a push, repair, replay, retarget, merge, changed membership, head/base, check attempt, review/thread state, or required-check policy. Refresh affected PRs and descendants rather than rescanning unrelated stacks. A base update may affect many stacks; mark their evidence stale and check each selected candidate against its current base immediately before merging. Repair dispatch still requires its immediate fresh signal/ownership read. Merge authorization always requires new complete reads of every remaining open PR under the whole-stack edit token, regardless of queue hints or prior selection evidence.

Reuse fresh observations only within their pass for status accounting and assignment decisions. A new published PR enters the next pending pass; it does not invalidate complete coverage of the captured set. Mark helper `plan` inventory complete only for the exact ledger PR set it evaluates. Partial refreshes or historical hints cannot supply `complete: true`. An incomplete batch-wide plan blocks assignments from that plan, not independently verified targeted repair selection below. Require current complete terminal states for the full ledger PR set before ending the watch.

### Targeted repair selection between full inventories

Keep a durable repair-candidate queue alongside the merge queue. Add ready stacks or published building prefixes with observed conflict, relevant unresolved review feedback, or current-head CI failure; preserve source/read times and incomplete observations separately. Queue entries are scheduling hints. Pending CI, missing approval, or unknown mergeability alone is not a repair signal. New publications on another stack must not postpone a repair whose own scope can be fully verified.

For a selected stack, recover its authorization, verified ready handoff or published-prefix evidence, complete registered membership, prior attempts, and active/reserved/uncertain owners. Refresh every member PR's current state, head repository/branch/SHA, base chain, mergeability, current-head latest checks/attempts, and paginated relevant reviews/comments/threads. Reconcile identity changes during reads. Require complete observations for this stack and successful exact-PR and head-repository/branch helper lookups. A held stack, a building stack without a safe build handoff, missing member data, an unknown lower-layer signal, conflicting ownership, or unfinished alignment defers that stack.

Before selecting conflict repair in a ready stack, process any eligible lower merge prefix under **Merge below a confirmed conflict**. Reconcile merge and alignment effects and refresh signals before reserving repair. Otherwise select the lowest open member with a verified repair signal; do not skip a blocked lower repair to mutate an upper member. Immediately recheck its signal, identity and owners, then use `suspend-build` for a building prefix or the normal whole-stack `acquire --mode reserved` for a ready stack, followed by the two-phase child handoff. Record selection mode `targeted-stack`, its complete inspected PR set and evidence, while retaining batch inventory completeness independently. Do not pass this subset as a complete batch `plan`, bypass reservation/START, or weaken merge gates. After a repair, refresh affected descendants before selecting more same-stack work. Full inventories and the helper's complete plan remain required for batch-wide planning and final termination accounting.

## Each bounded batch pass

In delegated mode, inventory capture/coverage is one inventory job; the targeted refresh/gate/merge/repair portions below run in independently allocated single-ready-stack maintenance jobs; building-prefix repair dispatch runs in the coordinator. No actor allocates global slots or starts a competing global pass. A slow inventory or stack never holds the coordinator in this procedure.

At every safe boundary reconcile prior merge/auto-merge effects and process eligible merge candidates first, then allocate confirmed merge-blocking `repair-pr` work, other repairs, publication, and new implementation in that order. Apply slop-fix-batch’s single-slot progress exception after two consecutive repair-displaced allocation boundaries only after gate/merge work and confirmed merge-blocking repairs. Set `unblocksMerge: true` only for a confirmed merge blocker in a complete, publication-verified ready stack. Preserve explicit capacity limits and within-queue priorities. Do not interrupt active workers or wait for blocked/pending candidates. Reapply this order after result collection and before each new assignment; targeted repair selection also follows it.

1. Honor an explicit watch stop before any repair assignment or merge. Record stopped state, disable and verify every pending auto-merge request owned by this batch under **Standalone auto-merge**, reconcile already submitted native requests and batch-owned queue entries under Native whole-stack merge’s stop rules, and collect already-finished results without starting new repairs or merges. Report uncertain cancellation or request outcomes. Stopping maintenance does not imply cancellation of running repairs or deletion of construction locks. Only an explicit human resume restarts a stopped watch.
2. Recover the ledger and helper `status`. Reconcile build owners, preparing/running/uncertain creations, reservations and claimed tokens, catalog recovery, prior pushes, thread outcomes, merge attempts/queue outcomes, post-merge alignment, and other managers. Reconcile an earlier merge against authenticated PR state before any new attempt; never repeat a confirmed merge. Reuse shared result collection, corrected retry, and comment rules. Keep incomplete, failed, ambiguous and externally blocked repairs recorded; do not call an idle or inaccessible agent complete.
3. Reconcile newly recorded ready handoffs with complete remote publication evidence. Update the same batch PR set from the ledger; this is inclusion of that batch's own outputs, not an issue rescan or authorization to adopt other PRs. Only ready stacks receive maintenance gate/merge jobs. A building stack’s verified published prefix may receive a coordinator-dispatched repair under **Repair a published building prefix**. Do not merge a building stack’s published prefix or mutate a held stack. A fully published ready stack may merge a passing lower prefix under **Merge below a confirmed conflict**. A registry transaction/error or missing authorization/ledger data defers assignment instead of creating a fresh run.
4. Select a periodic full inventory or the due incremental subset under **Inventory scope and candidate queue**. Include partial publications for status, repair-signal inspection and termination accounting and record which PRs were actually inspected. Include open/closed/merged state, exact head repository/branch/SHA, current base branch/SHA, mergeability, current-head checks and latest attempts, autoMergeRequest and queue state, and paginated relevant reviews/comments. Batch or parallelize independent reads and reconcile head/base changes during reads. Missing data is not a healthy result. Use this reference’s repair-signal assessment; pending checks, missing approval, or unknown mergeability alone do not trigger repair. Do not run the repository-mode default-branch filter in scanning, recovery, or dispatch.
5. Validate actual stack membership and current base chain, including GitHub retargeting after a parent merged. A legitimate base change does not exclude the recorded PR. Reconcile unfinished post-merge alignment under its recorded merge owner/token and pre-merge snapshot before evaluating fresh merge gates; do not acquire a second token or require passing CI before finishing that already authorized alignment. First verify any GitHub server-side alignment against the saved membership, boundaries and intended layer diffs. Accept verified completed alignment without replaying it locally; invoke `manage-stacked-prs` only for verified remaining alignment work. Native merge requests still pending/queued/uncertain prohibit local replay. Uncertain ancestry or concurrent membership changes block that stack rather than authorize a guessed replay. Closed/merged PRs receive no new repair and are never rewritten. Preserve original records; the stack's remaining open upper layers remain eligible when their current boundaries can be verified.
6. Collect available runtime status evidence and delivered agent messages/results under this reference’s Collect results rules, including its unavailable-handle reconciliation on later passes. Record target repairs separately from upper-only alignment, final remote heads, covered checks, push/review-thread outcomes, and ownership. Require alignment verification, not only a target push. Refresh head/base/check/review signals after a lower repair; discard obsolete upper signals. Do not assign another same-stack repair until ownership/effects are reconciled. Mark that affected stack due immediately and record a repair-result/alignment checkpoint. Continue other free stacks without waiting for all children.
7. First reconcile every batch-owned pending/uncertain auto-merge request, including requests removed from the candidate queue by a new blocker; perform required cancellation before repair selection. Update and drain the merge-candidate queue under **Merge complete stacks**, using fresh targeted whole-stack gates after result collection. Consider every ready stack over the recorded scan cadence; historical hints never establish a pass. Do not stop after the first processed stack. Pending CI/reviews in the selected merge range, active repairs, contention, or a failed/queued/uncertain merge defer only that stack; continue other free ready stacks in this pass. The helper's complete `plan` supports batch-wide repair selection and terminal accounting; targeted selection can dispatch fully verified individual ready stacks. Neither establishes merge readiness. Include pending/uncertain merges and unfinished alignment in active-stack accounting.
8. Refresh observations invalidated by result collection, merge, or cancellation before repair selection; if refresh is incomplete, do not label a global inventory complete. For a complete batch inventory, prepare the coordination helper's `plan` using these fresh reads, the implementation-ended flag, and all preparing/running/uncertain active stack IDs; require `complete: true` for assignments from that plan. Between full inventories, use **Targeted repair selection between full inventories** with complete fresh observations of each selected stack. Do not fill missing global plan rows with historical hints. Select the lowest open PR with a verified repair signal in each eligible ready stack or safely paused building prefix; reuse prior-attempt evidence to avoid repeating an already handled problem and to correct an incomplete attempt. If a lower signaled repair is blocked, do not skip it to mutate an upper layer; continue other stacks. External-log or missing-decision blockers remain associated with that stack, not a retry loop.
9. Immediately before dispatch, re-read the PR's open state, head/base, signal, stack and owners. Reserve a ready stack with `acquire --mode reserved`, or use the coordinator’s `suspend-build` for an eligible building prefix, and persist the attempt/token. Follow this reference’s worktree preparation and two-phase subagent start: spawn read-only preparation, record actual agent identity/worktree in the batch ledger and stack snapshot, then send the scoped start message. The child verifies assignment before claiming its reservation. Keep uncertain spawns/start deliveries reserved; release only after definite rejection or a confirmed stopped child with reconciled effects. Never assign two children to one reservation.
10. Re-evaluate termination using current complete terminal PR states for the full ledger PR set, including any publication recorded after pass start. End automatically only when the ledger says implementation ended, every published PR is closed/merged, and no active/uncertain publications, preparing/running/uncertain repairs, pending/uncertain merges, unfinished alignment, pending target-branch recovery, pending checkpoints, or unreconciled/incomplete stack ownership remains. Record completed management state after verifying the terminal PR states and reconciled ownership. An implementation still running, missing inventory, empty interim PR list, healthy open PRs, or an interrupted build is not completion. Report incomplete construction or unresolved ownership requiring action; never release it to make shutdown succeed.

One pass never waits for CI/reviews to settle or repeatedly retries the same failed command. Reuse **Recover incomplete repairs** below: a remaining verified repair signal may justify a new attempt after reconciling the previous effects and correcting the failure cause. This permission applies only to the fixed batch PR set. Report failures and required action, and stay quiet while state is unchanged or non-actionable.

## Repair signals and prior attempts

- For every inspected batch PR, read its current open/closed state, `baseRefName`, head and base SHAs, mergeability, checks, and all relevant review threads and comments, following pagination. Tie checks to the current head and latest relevant run attempt. Ignore superseded runs and previous-head failures. Reconcile a head or base change during inspection before using the evidence. Read check runs and commit statuses through the shared REST request entry point, paginate both sources, and inspect their structured results even when checks are failing or pending. Distinguish those results from authentication, transport, or parsing failures. Missing required data defers that PR; it is not a healthy result.
- A repair signal is a confirmed merge conflict (`mergeStateStatus: DIRTY` or `mergeable: CONFLICTING`), a current failing CI check, or an unresolved, non-outdated review thread containing `chatgpt-codex-connector[bot]` feedback. Recognize the equivalent bot login without the `[bot]` suffix when returned by GitHub. Let `$repair-pr` assess whether feedback is actionable, incorrect, duplicate, or blocked. Resolved/outdated threads, approvals, human-only feedback, pending checks, missing approval, and unknown mergeability alone do not trigger repair. An unrelated pending check or unknown mergeability does not suppress another verified signal. External checks without accessible logs remain report-only under `$repair-pr`; retain that blocker rather than dispatching it repeatedly.
- Before selecting a stack PR, look up its exact PR and head repository/branch in the shared coordination helper. A held stack, a building stack without an idle verified-prefix handoff, any reservation/repair/edit token, a registry transaction, or uncertain ownership defers assignment. A build token permits only its owner’s atomic `suspend-build`, never direct acquire or unlocked repair. Reconcile other watches and preparing subagents as well as the helper state.
- Healthy PRs receive no repair subagent. Merged or closed PRs receive no new repair, even if they were previously queued. Skip a PR owned by another preparing/running repair or ongoing maintenance automation, including ownership recorded outside this watch. Serialize PRs sharing a head repository/branch or checkout. Retain and report ownership or unsafe-workspace blockers rather than bypassing them.
- Compare signals with all prior attempts, including the final head and handled findings from a completed repair. Requeue after success only for a new problem or relevant changed evidence, such as a new review on the same head, a new current-head failing run, or a newly confirmed conflict. A timestamp change, a repair's own push, lingering old checks, or agent completion alone does not justify another run. When an attempt failed or ended before handling its assigned signal, apply **Recover incomplete repairs** even if the head and signal are unchanged. Reconcile uncertain side effects and workspace ownership before any retry.

## Recover target-branch CI

Use this procedure when an observed CI failure on the batch's target branch (normally `main`), or a shared failure in later batch PRs, indicates a possible interaction between merged changes. The original invocation authorizes diagnosis and recovery of regressions caused by the batch. Do not ask whether to make a corrective PR or reselect the merge strategy. Parallel standalone auto-merge remains the default; this procedure adds a temporary hold for affected merges, not repository settings changes or a new global serialization policy.

1. Verify the current target SHA, failing run/attempt and accessible logs through the shared API policy. Compare the failing code and tests with relevant merged batch changes and any available earlier passing evidence. Distinguish a confirmed batch regression from a stale run, an unrelated failure, or an unconfirmed flaky test. CI passing on separate PR heads does not prove that their combined changes work. Do not infer causation from merge order alone or add routine cumulative-tip validation.
2. Record one recovery entry per confirmed root cause in the existing maintenance record, with evidence files as needed. Preserve the original authorization, failing SHA/run, implicated batch PRs, affected stacks, owner/worktree, attempts and uncertain effects, corrective PR identity, exact validation SHAs/results, and remaining blockers. Link repeated downstream failures to that entry instead of dispatching duplicate fixes. Use existing coordinator-owned maintenance/operation events; preserve unrelated record fields. Do not change the canonical issue list, invent issue groups, or reuse a merged PR's identity.
3. Hold new merge requests and auto-merge setup for stacks whose eligibility is affected by the confirmed defect. For their pending batch-owned auto-merge requests, follow **Standalone auto-merge** cancellation and verification under the recorded owner/token. Reconcile queued/native requests and uncertain effects through their existing procedures before editing; a hold is not proof of cancellation. Do not cancel another actor's request. Continue independent construction, publication and unaffected merges under their normal gates. Keep this temporary hold in recovery evidence, not the human `stopped` state; recovery does not require a new human resume.
4. Repair an open batch PR through the existing ready-stack or published-prefix procedure when that is the appropriate source of the defect. For a defect already on the target branch, create a separate, minimal corrective PR from its freshly verified latest SHA in a clean isolated worktree. Never reopen or rewrite merged PRs, copy unrelated prerequisites, or revert unrelated work. The coordinator owns this supplemental recovery through construction, publication, subsequent repair and merge verification; this is the narrow exception to the prohibition on local repair for existing PR dispatch. Use the shared coordination helper to register a separate recovery branch under build ownership before edits. Record its coordination ID, token and operations in the maintenance recovery entry, rather than sending fixed-issue group/layer events or assigning an unrecorded stack to a delegated actor. Do not take over any active actor's work.
5. Implement the confirmed correction, run relevant automated checks under the batch validation policy, and publish with `$create-pr` and `$write-ste`. Reference the causal PRs and explain the regression; do not fabricate a new issue or add `Closes` for already-completed issues. Verify publication, runtime attachment, exact head/base and checks. Update the coordination registration, detach the clean checkout and transition the recovery stack to ready only after all corrective work and publication are verified. No cumulative/final-tip validation stage is added. Keep incomplete publication and uncertain writes protected and reconcile them before retrying.
6. The coordinator includes this supplemental record in each due pass and manages this recorded one-PR recovery stack using the same ownership, CI/review, standalone auto-merge, cancellation and verified-result gates as other complete standalone stacks. Its recovery entry supplies completion and membership evidence instead of fixed-issue group records; helper hints cannot certify this supplemental work. The affected-merge hold must permit the verified corrective PR that resolves its cause, but must not waive any of that PR's gates. Record the verified merge and inspect the relevant target-branch CI result for the merge or a descendant containing the fix. Keep recovery pending while that result is pending or unavailable, and investigate a remaining failure rather than declaring success from PR merge alone. Once recovery is verified, refresh affected PR checks, reviews and head/base evidence before lifting their holds and restoring eligible auto-merge. Do not reuse pre-recovery passing evidence.
7. If causation is unknown, continue scoped diagnosis and retain the uncertainty; if the failure is unrelated or external, record the evidence and actual blocker without expanding the repair scope. Do not waive failed PR gates or repeatedly dispatch inaccessible external-check failures. Ask only when progress requires specific missing authority, credentials/access, an unresolved user-owned change, or a concrete decision not supplied by the batch scope. Report the exact prerequisite, not a generic “How should we proceed?” or a choice of future merge strategies. Honor explicit stop instructions throughout recovery.

## Recover incomplete repairs

- Verify recorded published membership and ready-stack or building-prefix eligibility in **Dispatch a one-shot repair** before spawning or resuming a recovery subagent. A remaining signal requires the build handoff for building stacks; it does not authorize held-stack or unrelated PR mutation.
- Separate an unsuccessful attempt from a PR that requires an external prerequisite. A skipped merge conflict, wrong skill, exhausted review quota, missing approval, premature no-op, failed local validation, or agent execution error does not remove the PR from the repair queue. Reconcile the finished attempt, confirm the remaining current signal, and continue repair automatically within the original scope.
- Read the previous result and relevant commands. Verify which commits and pushes actually reached the PR, whether review-thread mutations succeeded, and whether a subagent, legacy chat, process, or automation still owns the branch. Preserve completed repairs and attempt history. Resolve uncertain creation, push, or mutation outcomes before creating replacement work; never run overlapping repairs.
- Correct the cause before retrying. For skill-discovery or workflow errors, expose and verify the actual `$repair-pr` installation. For a recoverable tool or environment failure, verify or repair the prerequisite. For code or validation failures, retain the concrete failure evidence and choose a corrective diagnostic or repair approach. Do not repeat an identical attempt without addressing its failure cause. Dispatch at most one new attempt for that PR in a bounded scan; reassess it on the next due pass instead of looping within the pass. This is not a concurrency cap across independent PRs.
- Once prior effects and ownership are reconciled, reuse a reachable stopped subagent with the runtime’s resume tool or spawn a replacement at the required model/settings under the original repair authorization. Pass the corrected approach and current assigned worktree/ownership in the handoff. Do not send follow-ups to legacy sidebar chats or create replacement chats. A fresh attempt uses the two-phase start below. If the prior owner is inaccessible or possibly still running, defer until it is confirmed stopped and its effects are reconciled.
- Require human action only for a concrete missing decision or authority that the original repair scope does not supply, unavailable credentials or access, or unresolved effects or user-owned changes that cannot be safely reconciled. Record the exact prerequisite and the evidence for it. Continue scanning that PR and retry when the prerequisite is available. An inaccessible external-check log remains report-only; a repeated identical external failure does not justify repeated dispatch. Missing review credits or a thumbs-up never gate conflict or CI repair.

## Repair a published building prefix

The coordinator may repair a published member before the stack's remaining groups finish. Keep the ledger and registry phase `building`; do not grant a ready-stack maintenance actor or enable any merge path. Select the lowest open member with a verified current repair signal under the existing scope and scheduler. These repairs have `unblocksMerge: false` until the stack is complete.

1. Stop assigning same-stack construction and let current assignments reach known completion; do not interrupt active work. Reconcile operations, publication attempts, owners and catalog effects. Require a completely verified existing published prefix, with no registered unpublished layer. This boundary does not require future groups to finish. Detach the clean integration checkout at the verified prefix tip under the build token. Other stacks remain eligible.
2. Reserve a normal repair slot and persist its assignment. Record the handoff operation before effects. Use the coordination helper's `suspend-build` with the current build owner/token, target PR, reservation owner and evidence file. Reconcile its outcome before retrying. Record the returned building reservation with ledger `build-repair-start`, then follow the normal preparation/identity/START/claim procedure below. Do not create a second owner or release the build lock first.
3. The repair owns only the assigned PR's code changes and necessary published upper-layer alignment. `$repair-pr` and `$manage-stacked-prs` reuse its claimed token and saved inherited boundaries. No trunk refresh, group reassignment, construction, merge or auto-merge is authorized. Keep uncertain effects and alignment protected. Return the token instead of calling `release` on a building stack.
4. Verify all existing prefix PR identities, heads, bases, intended diffs, original issue references and runtime attachment status. Capture repair/replay checks at the changed heads, saved old/new parent boundaries, and thread outcomes. Finish the repair assignment only when its actual effects are known. Under the retained token use `resume-build` with matching assignment and reconciled evidence, then apply ledger `build-repair-result` with full prefix publication verification, changed-layer coverage and the returned build token. Reconcile either helper write after interruption before retrying. Construction stays blocked in the ledger until both stores agree.
5. Preserve original worker checks and old publication history. Invalidate affected CI/review observations and checkpoints; refresh signals before another repair. Reattach the clean integration checkout to the verified updated top branch under build ownership before the next stack job. New dependent implementation starts at the repaired exact tip. For an already completed unintegrated result, compare its old prerequisites and acceptance against the new tip; record `prerequisiteRevalidation` on the new executor assignment when its required prerequisites changed, even when the old start is still an ancestor, adapt integration as needed and record `integrationChanged: true` with checks at the integrated head before publication. Do not reuse old-head coverage for changed integration code.

A definitively rejected spawn or a known no-op may return build ownership with stopped-child/effect evidence; unknown spawn, START, push, catalog, thread or alignment outcomes retain the reservation/repair ownership. Use the normal recovery procedure without marking the stack ready. If repair cannot finish, preserve the blocker and token and continue independent stacks.

## Dispatch a one-shot repair

1. Require a coordinator-reserved repair assignment and slot before spawning or resuming repair; a maintenance actor additionally requires its grant childAssignmentId. If no child slot is available, return the verified signal and finish this bounded actor job; the coordinator dispatches repair directly. Immediately before spawning or resuming a repair subagent, read the PR's current open state, head/base, signals, complete recorded stack membership, and owners. Require a verified ready batch stack or the coordinator’s verified published building-prefix handoff, not a repository default-branch or author match; missing reads defer assignment.
2. For every batch PR, verify registered published membership and reserve its whole stack under the shared coordination reference before spawning. Record the attempt, authorization pointer, and reservation token in the batch ledger and registered stack snapshot. For a building stack, only the build owner uses `suspend-build`; never use direct `acquire` or release its build protection. Leave uncertain reservations protected; release only after a definite rejected spawn or confirmed stopped child with reconciled effects.
3. Prepare a separate clean Git worktree serially in the recorded repository, using available worktree tools/conventions. Unless the human supplied a starting Git state, use a detached checkout at the freshly verified PR head SHA; `$repair-pr` owns the exact PR checkout after start authorization. Fetch the exact verified head through the appropriate remote if it is not available locally. Record its absolute path/SHA and verify the same Git common-directory root as the coordinator. Do not steal a checked-out branch, reuse user-owned changes, or substitute a separate clone.
4. Mark the attempt `preparing` with a unique task name containing the run label, PR number, and attempt number. Run `node /installed/slop-fix-batch/scripts/worker-settings.mjs repair --runtime <runtime>` using the resolved installed path, then pass its returned fields unchanged to the runtime’s creation tool. Follow [worker settings and context](worker-prompts.md#worker-settings-and-context), including for coordinator-dispatched repairs. Count preparing/running agents across the actual runtime tree when applying user/runtime limits; queue overflow without imposing another default cap.
5. The spawn message supplies the scoped handoff below and explicitly permits only read-only preparation until a start message arrives. Record the returned agent ID/canonical task name, worktree, and spawn outcome in the preallocated repair assignment through the scoped grant when dispatched by a maintenance actor, or directly by the coordinator, before any start message or subsequent spawn. Also persist that identity in the registered stack snapshot and batch ledger before START. A failed or uncertain spawn/start delivery must be reconciled before retrying; never create a duplicate to bypass a pending outcome.
6. Record the exact child start authorization in the preallocated assignment, then message that recorded agent through the runtime’s tool to authorize its attempt to start. If read-only preparation has already finished, resume the same agent with that START handoff as specified in [runtime tools](runtimes.md). Record delivery outcome immediately; reconcile uncertain delivery before retrying. Include its actual identity, assigned path, original authorization, and the recorded handoff/snapshot pointer (with reservation owner/token for stacks). The agent verifies its identity and assignment, then claims the reservation before checkout or writes.
7. Let `$repair-pr` own the one-shot workflow. The child uses only its assigned worktree, does not register automations, create sidebar chats, or merge PRs, and returns actual covered SHAs/checks, commits/pushes, review-thread outcomes, affected upper-layer alignment, remaining tokens, and blockers.

Supply resolved values, not literal placeholders:

- Exact PR URL and absolute installed `$repair-pr` skill/helper paths; instruct the child to read the skill before repair.
- Assigned absolute worktree path, starting SHA, repository/host, and common-directory root.
- Original human batch authorization, exact scope, explicit comment instructions/scope or none, and the batch validation constraints.
- Current repair signals and, for recovery, previous verified effects, failure cause, and corrected approach.
- Attempt/task name, coordinator identity and record pointer; coordination ID, snapshot/ledger path, reservation owner/token, and expected membership.
- Read-only preparation until the coordinator records the actual agent identity and sends the start handoff; then verify assignment before claiming ownership or mutating.
- Return results to this coordinator through agent messages/final output; preserve uncertain ownership and worktrees.

## Collect results

- Read delivered subagent messages/final outputs and available status evidence using [runtime tools](runtimes.md). Wait only when useful, for at most 30 seconds. Do not poll unchanged state or require all repairs to finish in one pass.
- Capture and verify each result before recording completion: exact commits/final heads, actual checks and covered SHAs, handled signals, push/review-thread outcomes, upper-layer alignment, blockers, uncertain effects, and remaining owners/tokens. An idle agent, no-op claim, or missing final output is not completion while its assigned repairable signal remains. A target push alone does not finish a stale stack. Pending follow-up CI is monitored by the next scan; do not claim pre-push checks cover new heads.
- On explicit continuation or runtime restart, reconcile recorded identities with available agent status/messages. If a handle is unavailable, preserve the attempt and inspect its worktree, pending Git/catalog operations, execution ownership, and authenticated remote outcomes. Absence from the current agent tree does not prove it stopped or released ownership. Require positive evidence that the prior owner stopped and effects are reconciled before transferring tokens or assigning replacement work. Use the shared recovery procedure for retained stack locks; if evidence is unavailable, report the blocker and continue other assignments.
- Keep completed/failed history and worktrees; there is no sidebar-chat creation, archiving, or creation directive. Preserve this coordinator after stopping the watch. Unexpected child automations or unresolved ownership remain blockers.
- For older repair chats, use read-only chat tools only to reconcile legacy results/owners. Messaging those chats still requires explicit human authorization; this workflow instead uses subagents after the old owner is confirmed stopped and effects are reconciled.

## Merge complete stacks

The maintenance coordinator owns this procedure. Before either merge path, check the maintenance recovery record for an affected-merge hold; only its verified corrective PR may proceed under that hold, with all normal gates still required. Do not wait for other stacks or the batch-wide `implementationEnded` flag. Process every eligible stack in each checkpoint or due pass. A blocked stack retains its recorded ownership and recovery state as required below while the coordinator continues other free ready stacks. An originally one-PR stack uses **Standalone auto-merge** below. Classify it only after all assigned groups have completed and full publication membership is verified; a prefix or a multi-PR stack reduced to one open layer is not standalone.

### Standalone auto-merge

Only an originally complete one-PR stack is eligible. Require recorded batch authorization, helper phase `ready`, all assigned groups implemented and validated, publication and runtime attachment status verified, correct standalone membership and target, non-draft state, and no active/uncertain repair, conflicting owner, or unfinished alignment. Acquire and record the whole-stack edit token and attempt before writing. Under that token, freshly read identity/head/base, complete reviews/threads, mergeability, current-head latest checks and required-check policy. Apply the existing review-pass rule below. Missing pages, unreadable policy, unknown/conflicting mergeability, or a confirmed current CI failure/cancellation/timeout block setup. Pending/in-progress or not-yet-reported required checks may wait in auto-merge only when the read is complete and required-check policy is known; never describe them as passed. GitHub enforces required checks and branch protection. Optional checks alone cannot guarantee GitHub will defer an immediate merge.

After review passes, invoke `$merge-pr` for that exact PR with the original batch authorization, verified head SHA and these gates: `gh pr merge <PR_URL> --squash --auto --match-head-commit <verified-head-sha>`. Keep the default subject; do not override admin rules or delete branches. Verify `state`, `mergedAt`, `mergeCommit`, `autoMergeRequest`, and any queue confirmation. Record actual merged, auto-merge enabled/pending, queue pending, failed, or uncertain outcomes. Auto-merge setup may merge immediately when GitHub's requirements are met. Record ownership only for a newly verified batch-enabled request; do not adopt or cancel a pre-existing request from another actor. Reconcile an unknown setup attempt before retry or deciding ownership. If auto-merge is unsupported, record that blocker and use a later fully passing normal merge attempt; do not retry an unchanged rejection or change repository settings.

Retain the token while effects are pending/uncertain and reconcile at later checkpoints or due passes without repeating the setup command. Pending state consumes no worker slot and does not block other stacks or implementation. On verified merge, record its commit, release reconciled ownership, and invalidate base observations for unstarted independent stacks. No descendant alignment is needed for a standalone PR.

If reviews cease to pass, identity/head/base changes, CI fails, repair becomes necessary, or the human stops the watch, disable a pending batch-owned auto-merge with `gh pr merge <PR_URL> --disable-auto` under its recorded token and freshly verify PR state and `autoMergeRequest`. If GitHub already merged it, record the merge and do not repair. Transfer/release ownership for repair only after the PR is verified open, auto-merge is absent, and no queue or unknown write effect remains. A queue registration requires confirmed withdrawal through a supported GitHub mechanism before edits; `--disable-auto` alone is not proof of queue withdrawal. Missing/uncertain cancellation or external ownership blocks only this PR's mutation and remains reported for reconciliation. A stop performs this cancellation reconciliation even though new setup, merges, and repairs are prohibited. Following a successful repair, require fresh review and identity gates at its new head before enabling auto-merge again.

### Whole-stack gates

These are the full gates for multi-PR stacks and standalone fallback merges. Standalone auto-merge uses the shared review rule here with its explicitly relaxed pending-CI gate above.

- Require explicit recorded merge authorization, helper phase `ready`, and verified completion of every assigned group: implementation, retained automated validation, publication, and applicable chat attachment. No held group, missing layer, active/uncertain repair, conflicting owner, or unfinished alignment may remain. A visible partial publication is insufficient. Validate the recorded membership and intended target/base chain. A closed-unmerged prerequisite blocks merging unless verified target-branch evidence establishes that its required changes are already present.
- Read every remaining open PR's current head/base, non-draft state, mergeability, paginated reviews/threads, checks and applicable required-check rules through authenticated GitHub. Reconcile concurrent changes before judging the stack. Missing or failed reads or inaccessible required-check policy defer merging. Unknown/conflicting mergeability blocks inclusion of that PR in the merge range; do not infer a pass from absence of retrieved data.
- Review passes when complete reads confirm no review records. When records exist, explicit approval is unnecessary: require no effective `CHANGES_REQUESTED` review and no unresolved, non-outdated review finding from any human or bot. Evaluate each reviewer's effective state, including later approvals and dismissals; an old request still blocks unless superseded or dismissed. Resolved/outdated threads and ordinary informational comments alone do not block. Do not manufacture approval or resolve a valid finding to obtain a pass. Human-only findings block merging but do not expand the existing bot-only repair assignment scope.
- CI passes only for the current head's latest relevant check/run attempts and applicable required checks. Failure, cancellation, timeout, pending/in-progress status, or a missing required check blocks merging. Superseded or old-head runs do not establish a pass or failure. Neutral/skipped non-required checks may be non-blocking; a required check must satisfy its configured passing rule. No checks count as pass only after verifying that none are required. Preserve pending and missing evidence separately from failure.
- Require every remaining open PR in the stack to pass these gates before starting or resuming merges, except for the explicitly selected lower prefix under **Merge below a confirmed conflict**. In that case every selected PR must pass; excluded upper blockers do not authorize their inclusion or waive full-stack reads and ownership. Gate evidence covers exact head/base SHAs; a repair, replay, retarget, or base/head change invalidates the affected evidence. GitHub branch protection remains authoritative even when this workflow treats absent reviews as passed.

### Merge below a confirmed conflict

This exception applies only to an originally multi-PR, fully published `ready` stack with every assigned group complete. It never permits merging a building prefix. Under the same whole-stack edit token and fresh complete member reads, identify the lowest open PR with a confirmed conflict (`DIRTY` or `CONFLICTING`). Starting at the lowest open layer, select the longest contiguous prefix below that conflict whose members each pass every merge gate. Stop at the first failed, pending, unknown or incomplete gate; never skip a PR. Without a confirmed conflict, keep the normal whole-stack policy. If the prefix is empty, use existing repair or wait handling.

Record the selected PRs/top/head, full stack membership, conflict boundary, and every remaining layer’s old inherited parent boundary and intended diff in existing operation/observation evidence. Process this prefix before dispatching conflict repair. Prefer the native procedure below with its selected top PR; verify that the request includes exactly this prefix. A conflict is not evidence that native merging is unsupported. Use sequential fallback only after unsupported capability is established.

After verified merges, reconcile server-side rebases and retargets before any local replay. Reuse the merge token and saved boundaries to align only affected, still-open descendants, excluding already-squashed commits. For `A → B → C → D` with passing A/B and conflicting C, a completed A/B merge leaves only C/D for replay and necessary conflict resolution. Never rewrite merged layers. In sequential fallback, merging A can require aligning still-open B and its descendants before B can pass fresh gates; do not defer required alignment or reuse B’s old-head checks merely to finish the selected prefix. Recompute the eligible prefix after each merge/alignment rather than treating the initial selection as continuing authority.

Pending, queued or uncertain merge/server-side effects prohibit local replay and repair dispatch. Retain ownership and reconcile them first. Accept verified server alignment without repeating it; use `manage-stacked-prs` only for remaining alignment, with focused validation for conflict resolutions. Refresh reviews/checks at changed heads and bases, and dispatch any remaining verified repair signal through the existing repair workflow after ownership is reconciled. Record partial completion per PR; the stack is complete only when all its PRs are verified merged. On resume, finish outstanding alignment before selecting another merge and never repeat a verified merge.

### Native whole-stack merge

Prefer GitHub's native whole-stack merge for an originally multi-PR stack. Consult the current [stack merging documentation](https://docs.github.com/en/pull-requests/get-started/about-stacked-prs) and host-specific [asynchronous merge API](https://docs.github.com/en/rest/pulls/pulls#merge-a-pull-request-asynchronously). Merging the top PR includes the open layers below it; merging a lower PR can cause server-side descendant rebasing. Read-only host/version documentation and verified remote stack membership must establish support. Do not assume `gh pr merge` uses the asynchronous stack API, or use a real write as a capability probe. Record unsupported native capability and use **Sequential fallback: merge, align, and resume** only when that limitation is established. Incomplete discovery defers that stack; a permission, CI, review, conflict, transport, or unknown-outcome error is not evidence of unsupported capability.

1. Acquire and record the same whole-stack `edit` token and attempt used by sequential merging. Under it, perform fresh complete **Whole-stack gates** and select either all remaining open layers or the passing prefix allowed by **Merge below a confirmed conflict**. Verify that the selected top PR’s native merge includes exactly the selected batch PRs in the recorded order and base chain, with no excluded upper or unrelated lower layers. Snapshot every remaining member’s head/base SHA, intended diff and inherited boundaries, including descendants outside the selected merge range. If only one original layer remains and GitHub no longer reports a native stack object, verify that its base is the original target, all recorded prerequisites are merged into that target, and no downstack PR would be included; use the same asynchronous API with whole-stack gates and no auto-merge. Recheck identities/membership immediately before the request; changed or incomplete data defers the attempt. The top expected SHA does not protect lower heads, so never treat it as a replacement for these per-member checks.
2. The maintenance owner submits one authenticated `PUT /repos/{owner}/{repo}/pulls/{top-number}/merge-async` through the shared request entry point, using the supported host API version, `sha` equal to the verified top head, `merge_method: squash`, `merge_action: default`, and `bypass_rules: false`. Preserve GitHub's default commit subjects by omitting custom title/message. Inspect a 409's returned UUID/options as a pre-existing request; do not claim it as batch-owned unless the ledger and remote evidence establish ownership. Do not enable auto-merge, bypass a configured merge queue, delete branches, or invoke the single-layer `$merge-pr` command for this native request. Persist the attempt and evict affected cache entries before sending; record the returned request UUID/status and invalidate observations after the attempt. GitHub's branch rules remain authoritative. The API merge_method applies only to direct merges; when a merge queue is configured, freshly verify its configured merge method is squash before submitting. Missing policy or a different method blocks this stack; do not bypass the queue or change repository settings. This is a batch-only maintenance-owner operation; `$merge-pr` still owns standalone and sequential fallback commands.
3. Treat HTTP acceptance, `pending`, and `enqueued` as pending outcomes. Retain whole-stack ownership while a request, queue entry, or effect is pending/uncertain. Reconcile an available UUID with `GET /repos/{owner}/{repo}/pulls/{top-number}/merge-async/{uuid}` and separately verify each recorded PR's actual state, `mergedAt`, and merge commit SHA. An API `merged` status alone does not prove every member completed; an `enqueued` result is not a merge. Never resubmit or switch to sequential fallback while prior effects are unresolved. Record verified partial progress per PR without calling the whole stack complete. Reconcile a lost/expired UUID from authenticated PR, stack, ref and queue state; a missing result is not proof of failure.
4. When every recorded stack PR is verified merged, record per-PR merge commit SHAs, invalidate unstarted-stack base observations, record stack completion, and release reconciled ownership. Completion of a selected prefix alone is partial progress, not stack completion. No descendant replay is needed for a fully merged stack. Invalidate base observations for unstarted stacks as soon as any member merge is verified, including partial completion. If only a prefix merged, first reconcile the operation and any server-side rebase/retarget against saved diffs and boundaries. Do not replay descendants already aligned by GitHub. Use `manage-stacked-prs` only for proven remaining alignment work after no request/queue/unknown effect remains. A completed alignment makes this stack due immediately. Freshly read and gate the remaining stack before another native request, selecting its merge range under **Whole-stack gates** and the confirmed-conflict exception. Never use old-head CI.
5. On a definite failure, reconcile per-member remote/queue state before releasing ownership. Retry only after a corrective cause or changed readiness, never an unchanged rejection in the same pass. Continue other free stacks without waiting. A stop prevents new requests and records stopped management state; reconcile already submitted requests and actual member outcomes. Withdraw batch-owned queue entries only through a supported mechanism and verify withdrawal. Do not claim a submitted direct merge can be cancelled; retain pending/uncertain ownership and report any irreversible completion or unresolved effects for recovery.

### Sequential fallback: merge, align, and resume

Use this procedure for originally multi-PR stacks only when native whole-stack merging is verified unsupported, and for fully passing standalone fallback merges. Eligible standalone auto-merge follows its separate procedure above.

1. Before any merge or ref change, acquire the existing helper's whole-stack `edit` token with `acquire --stack <id> --owner <merge-owner> --mode edit --pr <lowest-open-pr-url>`. Persist the owner/token and attempt before writes. Under that token, freshly re-read ownership, membership, and every remaining open PR's head/base, non-draft state, mergeability, complete reviews/threads, current-head latest checks and required-check policy. A pass inventory selects candidates only; it cannot replace these whole-stack gates, even when head/base SHAs match. Defer on contention, incomplete reads, or concurrent changes; never run a repair alongside this merge owner. Snapshot each remaining child's verified old inherited parent boundary and layer diff before the parent's squash merge changes ancestry.
2. Invoke `$merge-pr` for the lowest open layer only. Supply the original human batch authorization, exact PR URL, verified head SHA, fresh whole-stack observations and passing gates for the selected merge range, and constraints: squash, default commit subject, no auto-merge/admin override/branch deletion, and no advancement on a failed, queued or uncertain result. Use `gh pr merge <PR_URL> --squash --match-head-commit <verified-head-sha>`; let the merge skill verify the result. Its direct-invocation no-preflight and `--auto` defaults do not override this narrower handoff.
3. Confirm `state`, `mergedAt`, and merge commit SHA through authenticated GitHub before advancing. Record the actual result immediately. Queue registration or an open PR is pending, not merged. Retain the stack token for queued/uncertain effects and reconcile on a later checkpoint or due pass; never rewrite a queued PR. A confirmed failure with no pending effects may release ownership after reconciliation, retaining its blocker. Do not repeat a failed command in the same pass, or retry an unchanged rejection on later checkpoints or due passes without a corrective cause or changed readiness.
4. If no open descendants remain after a verified merge, record completion and release the reconciled stack token. Otherwise inspect authenticated remote heads, bases and diffs for GitHub’s automatic descendant alignment first. Accept it only when the saved inherited boundaries and intended layer diffs prove it complete. If verified alignment work remains and no server-side operation is pending/uncertain, invoke `manage-stacked-prs` to align only those remaining open descendants, reusing this merge owner's token and the pre-merge boundary snapshot. The new lowest open layer must target the original selected repository base containing the verified squash commit. Replay only each child's own commits onto its verified new parent; do not carry the already-squashed lower commits forward. Preserve each layer's intended diff, required validation, scoped pushes and catalog locking. Never rewrite merged/queued PRs or unrelated stacks. Uncertain boundaries or effects stop that stack with its token retained for recovery.
5. Verify remote heads, bases, layer diffs and completed alignment. Refresh all remaining open PR reviews and CI for their new heads/bases; prior passing checks do not cover rewritten heads. If every remaining PR passes every gate, or a fresh confirmed-conflict selection yields a passing lower prefix, continue bottom-to-top in this bounded pass within that eligible range. If no merge range is eligible because checks are pending or gates fail, record the exact remaining boundary and release the token only when all merge/alignment effects are known and no queue or Git/catalog operation remains. Continue other free ready stacks without waiting. Resume this stack on a later checkpoint or due pass after fresh whole-stack gating; completed lower merges stay recorded. Repairable signals may then use the existing dedicated repair workflow.
6. On continuation, reconcile PR states, merge commit SHAs, queue outcomes, remote refs, alignment snapshot and ownership before retrying. If a parent already merged, finish its outstanding alignment rather than merging it again. An absent queue indication alone is not proof that a previous uncertain attempt failed. Release the token after verified completion or a reconciled stop with no outstanding effects. Record completed descendant alignment as an immediate checkpoint at the next safe boundary. Keep pending/uncertain attempts and alignment in termination accounting; notify only meaningful outcomes, failures or required action.
