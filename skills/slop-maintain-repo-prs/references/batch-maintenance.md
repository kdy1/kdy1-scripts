# Maintenance delegated by Slop Fix Batch

Use this mode only for the exact batch delegated by a human's explicit `$slop-fix-batch` invocation. Skill editing or a ledger path without its human authorization is insufficient. Repository-mode default-branch/author filters and indefinite lifetime do not apply here. Do not change any existing repository-mode watch or its heartbeat to batch mode.

Read [$repair-pr](../../repair-pr/SKILL.md), its [shared coordination reference](../../repair-pr/references/stack-coordination.md), and [$manage-stacked-prs](../../manage-stacked-prs/SKILL.md). Retain the batch's validation policy for delegated repairs: skip manual app launches, real-environment reproduction, and validation screenshots; run required automated checks and disclose skipped validation. Preserve the repair comment policy. Also read [$merge-pr](../../merge-pr/SKILL.md). The original batch invocation delegates conditional merging of complete passing stacks to this coordinator under **Merge complete stacks** below. Repair subagents never merge. Never enable auto-merge. Editing these skills does not merge live PRs, update saved automations, or expand an older watch's authorization; an older repair-only watch requires explicit human merge authorization before its record and heartbeat gain this policy.

## Establish the batch watch

1. Recover the original human invocation, batch ID, durable absolute ledger path, host/repository, repository checkout, push remote, coordination root, stack IDs and catalog IDs, ordered layers/PR URLs, ready/publication evidence, and construction owners. Verify the recorded publication against authenticated GitHub and confirm the clean integration checkout was detached at its verified tip; do not adopt existing fixing PRs that the batch only reported. The complete target set is every recorded published PR from this batch, including upper layers. Do not filter by author or default base and do not search for additional PRs. A PR remains in the ledger after closure/merge or base retargeting; never create a replacement PR for it.
2. Verify the repository checkout and absolute `repair-pr` skill/helper paths, its `manage-stacked-prs` dependency, `merge-pr`, squash merging with `--match-head-commit`, shared common-directory root, authenticated GitHub access, and scheduling/subagent/worktree tools as in repository-mode preflight. Repairs use `collaboration.spawn_agent` with `model: "gpt-6-luna"`, `reasoning_effort: "xhigh"`, and `fork_turns: "none"`. Follow the main skill's two-phase repair handoff; pass the batch authorization, validation/comment scope, and coordination record. Do not substitute a model, reasoning effort, standalone automation, sidebar chat, or local repair. The common directory must match in every repair worktree.
3. Keep one maintenance record in the existing batch ledger and this coordinating chat. Add mode `batch`, implementation-ended flag, automation ID/state and uncertain outcomes, cadence, exact delegated PR identities/order, original authorization and comment scope, attempt history/spawn outcomes/actual agent IDs/task names/worktrees/start handoffs, ownership/reservation/claimed tokens, final heads/alignment and thread outcomes, result-capture and ownership-reconciliation state, skipped validation, and blockers. Retain merge authorization, each stack's assigned-group completion, gate evidence tied to exact head/base SHAs, effective review requests/thread IDs, current check/run IDs and required-check expectations, merge owner/token, attempts and queue/uncertain outcomes, merge commit SHAs, pre-merge inherited boundaries, and post-merge alignment/validation results. Record pending/active checkpoint events, the pass identity and captured PR set, inventory completeness and per-PR read times, and invalidated observations. The same coordinating owner serializes batch-ledger writes for construction and maintenance; workers return results instead of editing that ledger. Atomic helper state owns locks; the ledger owns human authorization and creation/repair history. Reconcile both on every continuation.
4. Discover existing automations through the tool's documented mechanism (`$CODEX_HOME/automations/*/automation.toml`) and match batch ID, this chat, repository, and ledger. Reuse the matching heartbeat. If another chat owns it, report that owner instead of registering a competing heartbeat. Reconcile overlapping repository watches, repair subagents, and legacy repair chats before assignment; use the shared whole-stack reservation so only one owner can dispatch. Do not widen an existing general watch's query to include the batch.
5. Register the first heartbeat when the first stack has passed complete publication verification and the helper's `ready` transition. Subsequent ready handoffs update the same ledger and watch; no new heartbeat is created. Preserve an existing or user-specified interval; default a new watch to five minutes. There is no default total concurrency cap. Share the explicit human limit and runtime capacity with all active/reserved investigation, preparation, implementation, publication, nested, and repair workers. The separate publication limit does not add slots or reserve capacity. Reconcile slot accounting with construction before dispatch, retaining uncertain starts. At safe boundaries collect results and refill eligible implementation slots before assigning maintenance repairs; do not wait for other workers, publishers, or CI/reviews. Preserve at most one preparing/running repair per stack. Distinct ready stacks dispatch in parallel.
6. Use `automation_update` to create/reuse one heartbeat in this coordinating chat with the saved prompt below, filling all placeholders. Preserve notification preferences and unrelated fields. Record and reconcile the actual registration result before dispatch. A creation failure leaves publication intact and maintenance reported inactive/uncertain; retry only after reconciling whether registration occurred. Immediately perform one bounded scan after successful registration, then return to implementation without waiting for repair completion.

Local maintenance requires the computer and Codex app to remain running. If no PRs were published, do not register a heartbeat. An interrupted or held stack remains construction-protected and is reported as a blocker; its visible partial PRs do not authorize repairs.

## Construction checkpoints

After at least one verified ready handoff, record a pending checkpoint for group publication or stack ready handoff, implementation-result collection, completed group integration or cumulative-tip validation, and immediately before implementation returns its final report. The final checkpoint follows the ledger's `implementationEnded: true` update. Coalesce pending events at the next coordinator safe boundary into one **Each bounded batch pass**. The registration scan counts as the first handoff's pass. Do not start a full CI/review inventory for every individual PR publication or wait for all active publishers to finish. Construction dispatches publishable groups promptly; maintenance may process other ready stacks while those publishers run. These calls reuse this batch's ledger, coordinator, and single heartbeat. Preserve the existing cadence or the five-minute default; do not register another schedule or wait for the next tick.

Honor a stopped watch. Reconcile inactive/uncertain registration through **Establish the batch watch** before assignments or merges. Persist the pass identity and checkpoint events it consumes at start. Events and new publication results arriving during that pass remain pending for the next pass at a safe boundary; do not restart the inventory or start a competing pass. Construction calls after releasing its catalog token and reconciling its current Git/gh-stack operation, while retaining building/held stack protection. Publishers on other stacks may remain active. Collect their results and refill implementation slots at safe boundaries within maintenance. Keep catalog mutations serialized with construction, holding that token through each whole command and outcome reconciliation even when it performs network I/O. Checkpoint passes use all normal ownership, fresh-read, recovery, and whole-stack gates. They never wait for CI/reviews or all repairs to finish. Scheduled passes continue after implementation ends under the same termination rules.

## Inventory scope and candidate queue

Capture the recorded PR set at pass start and record the inspected subset separately. Perform complete authenticated inventories at registration, when recovering missing coverage, at a recorded periodic full-scan interval, and before final termination accounting. Between full scans, refresh new publications, changed or invalidated observations, and due pending or unknown results. Choose and record the full-scan interval and next refresh times without changing the heartbeat cadence. Publication checks remain limited to the affected prefix. Use grouped requests or bounded parallel read chunks and fetch every page needed for each inspected PR's checks, reviews, comments, threads, and policy. Record identity, exact head/base SHAs, read time, check/run attempts, gate state, source inventory, and completeness. Missing or failed pages remain unknown; an incremental pass is not a complete batch inventory.

Keep a separate durable merge-candidate queue. Add a complete ready stack only when complete observations indicate that every remaining open layer passes its gates at the recorded heads and base chain. Use the queue to select targeted whole-stack checks promptly at safe boundaries, without waiting for another full inventory or heartbeat. Historical candidates may survive a pass as scheduling hints only. Expire gate evidence at pass end; unchanged head/base SHAs never prove that checks, reviews, or policy stayed unchanged. Remove or suspend candidates after a verified blocker, changed head or membership, terminal state, ownership conflict, or unfinished alignment. Unknown or changing mergeability permits a later bounded targeted check, never a merge or a repair by itself. Continue other candidates rather than polling that stack.

Invalidate affected gate observations on a push, repair, replay, retarget, merge, changed membership, head/base, check attempt, review/thread state, or required-check policy. Refresh affected PRs and descendants rather than rescanning unrelated stacks. A base update may affect many stacks; mark their evidence stale and check each selected candidate against its current base immediately before merging. Repair dispatch still requires its immediate fresh signal/ownership read. Merge authorization always requires new complete reads of every remaining open PR under the whole-stack edit token, regardless of queue hints or prior selection evidence.

Reuse fresh observations only within their pass for status accounting and assignment decisions. A new published PR enters the next pending pass; it does not invalidate complete coverage of the captured set. Mark helper `plan` inventory complete only for the exact ledger PR set it evaluates. Partial refreshes or historical hints cannot supply `complete: true`; defer new repair assignments until the required captured inventory is complete. Already-owned repairs can still be collected, and independently refreshed ready stacks can still be gated for merging. Require current complete terminal states for the full ledger PR set before ending the watch.

## Each bounded batch pass

1. Honor an explicit watch stop before any repair assignment or merge. Record stopped state, deactivate the recorded heartbeat, and collect already-finished results without starting new repairs or merges. Report uncertain deactivation. Stopping maintenance does not imply cancellation of running repairs or deletion of construction locks. Only an explicit human resume restarts a stopped watch.
2. Recover the ledger and helper `status`. Reconcile build owners, preparing/running/uncertain creations, reservations and claimed tokens, catalog recovery, prior pushes, thread outcomes, merge attempts/queue outcomes, post-merge alignment, and other managers. Reconcile an earlier merge against authenticated PR state before any new attempt; never repeat a confirmed merge. Reuse shared result collection, corrected retry, and comment rules. Keep incomplete, failed, ambiguous and externally blocked repairs recorded; do not call an idle or inaccessible agent complete.
3. Reconcile newly recorded ready handoffs with complete remote publication evidence. Update the same delegated PR set from the ledger; this is inclusion of that batch's own outputs, not an issue rescan or authorization to adopt other PRs. Only stacks whose helper phase is `ready` can be assigned. Early group publication leaves a stack building/held until every assigned group is complete; do not repair or merge its published prefix. Do not alter building or held stacks. A registry transaction/error or missing authorization/ledger data defers assignment instead of creating a fresh run.
4. Select a periodic full inventory or the due incremental subset under **Inventory scope and candidate queue**. Include partial publications solely for status/termination accounting and record which PRs were actually inspected. Include open/closed/merged state, exact head repository/branch/SHA, current base branch/SHA, mergeability, current-head checks and latest attempts, and paginated relevant reviews/comments. Batch or parallelize independent reads and reconcile head/base changes during reads. Missing data is not a healthy result. Use the main skill's repair-signal assessment; pending checks, missing approval, or unknown mergeability alone do not trigger repair. Do not run the repository-mode default-branch filter in scanning, recovery, or dispatch.
5. Validate actual stack membership and current base chain, including GitHub retargeting after a parent merged. A legitimate base change does not exclude the recorded PR. Reconcile unfinished post-merge alignment under its recorded merge owner/token and pre-merge snapshot before evaluating fresh merge gates; do not acquire a second token or require passing CI before finishing that already authorized alignment. Reconcile it under `manage-stacked-prs`; uncertain ancestry or concurrent membership changes block that stack rather than authorize a guessed replay. Closed/merged PRs receive no new repair and are never rewritten. Preserve original records; the stack's remaining open upper layers remain eligible when their current boundaries can be verified.
6. Prepare the coordination helper's `plan` inventory using these fresh reads, the implementation-ended flag, and all preparing/running/uncertain active stack IDs. Require `complete: true` for new assignments. Select the lowest open PR with a verified repair signal in each free ready stack; reuse prior-attempt evidence to avoid repeating an already handled problem and to correct an incomplete attempt. If a lower signaled repair is blocked, do not skip it to mutate an upper layer; continue other stacks. External-log or missing-decision blockers remain associated with that stack, not a retry loop.
7. Immediately before dispatch, re-read the PR's open state, head/base, signal, stack and owners. Reserve the whole stack with `acquire --mode reserved` and persist the attempt/token. Follow the main skill's worktree preparation and two-phase subagent start: spawn read-only preparation, record actual agent identity/worktree in the batch ledger and stack snapshot, then send the scoped start message. The child verifies assignment before claiming its reservation. Keep uncertain spawns/start deliveries reserved; release only after definite rejection or a confirmed stopped child with reconciled effects. Never assign two children to one reservation.
8. Collect bounded `collaboration.list_agents` snapshots and delivered agent messages/results under the main skill's Collect results rules, including its unavailable-handle reconciliation on later heartbeats. Record target repairs separately from upper-only alignment, final remote heads, covered checks, push/review-thread outcomes, and ownership. Require alignment verification, not only a target push. Refresh head/base/check/review signals after a lower repair; discard obsolete upper signals. Do not assign another same-stack repair until ownership/effects are reconciled. Continue other free stacks without waiting for all children.
9. Update and drain the merge-candidate queue under **Merge complete stacks**, using fresh targeted whole-stack gates after result collection. Consider every ready stack over the recorded scan cadence; historical hints never establish a pass. Do not stop after the first processed stack. Pending CI/reviews, active repairs, contention, or a failed/queued/uncertain merge defer only that stack; continue other free ready stacks in this pass. The helper's `plan` selects repairs and determines terminal accounting; it does not establish merge readiness. Include pending/uncertain merges and unfinished alignment in active-stack accounting.
10. Re-evaluate termination using current complete terminal PR states for the full ledger PR set, including any publication recorded after pass start. End automatically only when the ledger says implementation ended, every published PR is closed/merged, and no active/uncertain publications, preparing/running/uncertain repairs, pending/uncertain merges, unfinished alignment, pending checkpoints, or unreconciled/incomplete stack ownership remains. Record completion and deactivate this batch's heartbeat; verify the tool result. An implementation still running, missing inventory, empty interim PR list, healthy open PRs, or an interrupted build is not completion. Report incomplete construction or unresolved ownership requiring action; never release it to make shutdown succeed.

One pass never waits for CI/reviews to settle or repeatedly retries the same failed command. Reuse the main skill's corrected automatic recovery: a remaining verified repair signal may justify a new attempt after reconciling the previous effects and correcting the failure cause. This permission applies only to the fixed delegated PR set. Report failures and required action, and stay quiet while state is unchanged or non-actionable.

## Merge complete stacks

The maintenance coordinator owns this procedure. Do not wait for other stacks or the batch-wide `implementationEnded` flag. Process every eligible stack in each checkpoint or scheduled pass. A blocked stack retains its recorded ownership and recovery state as required below while the coordinator continues other free ready stacks. A one-PR stack follows the same gates.

### Whole-stack gates

- Require explicit recorded merge authorization, helper phase `ready`, and verified completion of every assigned group: implementation, retained automated validation, publication, and attachment. No held group, missing layer, active/uncertain repair, conflicting owner, or unfinished alignment may remain. A visible partial publication is insufficient. Validate the recorded membership and intended target/base chain. A closed-unmerged prerequisite blocks merging unless verified target-branch evidence establishes that its required changes are already present.
- Read every remaining open PR's current head/base, non-draft state, mergeability, paginated reviews/threads, checks and applicable required-check rules through authenticated GitHub. Reconcile concurrent changes before judging the stack. Missing or failed reads, unknown/conflicting mergeability, or inaccessible required-check policy defer merging; do not infer a pass from absence of retrieved data.
- Review passes when complete reads confirm no review records. When records exist, explicit approval is unnecessary: require no effective `CHANGES_REQUESTED` review and no unresolved, non-outdated review finding from any human or bot. Evaluate each reviewer's effective state, including later approvals and dismissals; an old request still blocks unless superseded or dismissed. Resolved/outdated threads and ordinary informational comments alone do not block. Do not manufacture approval or resolve a valid finding to obtain a pass. Human-only findings block merging but do not expand the existing bot-only repair assignment scope.
- CI passes only for the current head's latest relevant check/run attempts and applicable required checks. Failure, cancellation, timeout, pending/in-progress status, or a missing required check blocks merging. Superseded or old-head runs do not establish a pass or failure. Neutral/skipped non-required checks may be non-blocking; a required check must satisfy its configured passing rule. No checks count as pass only after verifying that none are required. Preserve pending and missing evidence separately from failure.
- Require every remaining open PR in the stack to pass these gates before starting or resuming merges. Gate evidence covers exact head/base SHAs; a repair, replay, retarget, or base/head change invalidates the affected evidence. GitHub branch protection remains authoritative even when this workflow treats absent reviews as passed.

### Merge, align, and resume

1. Before any merge or ref change, acquire the existing helper's whole-stack `edit` token with `acquire --stack <id> --owner <merge-owner> --mode edit --pr <lowest-open-pr-url>`. Persist the owner/token and attempt before writes. Under that token, freshly re-read ownership, membership, and every remaining open PR's head/base, non-draft state, mergeability, complete reviews/threads, current-head latest checks and required-check policy. A pass inventory selects candidates only; it cannot replace these whole-stack gates, even when head/base SHAs match. Defer on contention, incomplete reads, or concurrent changes; never run a repair alongside this merge owner. Snapshot each remaining child's verified old inherited parent boundary and layer diff before the parent's squash merge changes ancestry.
2. Invoke `$merge-pr` for the lowest open layer only. Supply the original human delegation, exact PR URL, verified head SHA, passing whole-stack evidence, and constraints: squash, default commit subject, no auto-merge/admin override/branch deletion, and no advancement on a failed, queued or uncertain result. Use `gh pr merge <PR_URL> --squash --match-head-commit <verified-head-sha>`; let the merge skill verify the result. Its direct-invocation no-preflight and `--auto` defaults do not override this narrower handoff.
3. Confirm `state`, `mergedAt`, and merge commit SHA through authenticated GitHub before advancing. Record the actual result immediately. Queue registration or an open PR is pending, not merged. Retain the stack token for queued/uncertain effects and reconcile on a later checkpoint or heartbeat; never rewrite a queued PR. A confirmed failure with no pending effects may release ownership after reconciliation, retaining its blocker. Do not repeat a failed command in the same pass, or retry an unchanged rejection on later checkpoints or heartbeats without a corrective cause or changed readiness.
4. If no open descendants remain after a verified merge, record completion and release the reconciled stack token. Otherwise invoke `manage-stacked-prs` to align only the remaining open descendants, reusing this merge owner's token and the pre-merge boundary snapshot. The new lowest open layer must target the original selected repository base containing the verified squash commit. Replay only each child's own commits onto its verified new parent; do not carry the already-squashed lower commits forward. Preserve each layer's intended diff, required validation, scoped pushes and catalog locking. Never rewrite merged/queued PRs or unrelated stacks. Uncertain boundaries or effects stop that stack with its token retained for recovery.
5. Verify remote heads, bases, layer diffs and completed alignment. Refresh all remaining open PR reviews and CI for their new heads/bases; prior passing checks do not cover rewritten heads. If every remaining PR passes every gate, continue bottom-to-top in this bounded pass. If checks are pending or gates fail, record the exact remaining boundary and release the token only when all merge/alignment effects are known and no queue or Git/catalog operation remains. Continue other free ready stacks without waiting. Resume this stack on a later checkpoint or heartbeat after fresh whole-stack gating; completed lower merges stay recorded. Repairable signals may then use the existing dedicated repair workflow.
6. On continuation, reconcile PR states, merge commit SHAs, queue outcomes, remote refs, alignment snapshot and ownership before retrying. If a parent already merged, finish its outstanding alignment rather than merging it again. An absent queue indication alone is not proof that a previous uncertain attempt failed. Release the token after verified completion or a reconciled stop with no outstanding effects. Keep pending/uncertain attempts and alignment in termination accounting; notify only meaningful outcomes, failures or required action.
