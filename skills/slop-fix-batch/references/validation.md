# Validation policy

Skip direct app launches, manual reproduction, validation in a real environment, and screenshot capture for validation, even when an issue requests them. Keep automated tests, builds, linters, code inspection during investigation and implementation, and Git/GitHub state verification. Automated tests may launch the app or exercise reproduction scenarios as part of the test suite.

For implementation and PR publication, assess completion against the implementation requirements and passing implementation-worker checks. There is no cumulative-tip or final-tip validation stage. Run required automated checks, including whole-repository checks required for the assigned change, in the implementation worker before handoff. Do not defer them to integration. Preserve Git hooks. If integration changes code through conflict resolution or adaptation, run only the checks needed to cover that change before publication and dependent implementation; record their exact SHA. An unchanged cherry-pick does not require a second validation pass. Report worker coverage at its original SHA; never claim it validated another tip. Skipped real-world validation alone does not block publication or make an implemented issue partial. Include a standalone `Closes` line for each such issue; do not downgrade it to `Refs` solely because real-world validation was skipped. Record skipped validation as not performed in the ledger, worker handoffs, PR bodies, and final report. Never claim it passed.

This policy does not relax the evidence requirements for directly closing already-resolved issues below. Use existing evidence for required release or environment acceptance; if that evidence is insufficient, leave the issue open without performing the skipped validation.
