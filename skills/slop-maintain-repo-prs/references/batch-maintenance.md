# Maintenance delegated by Slop Fix Batch

Use this mode only for the exact batch delegated by a human's explicit `$slop-fix-batch` invocation. Skill editing or a ledger path without its human authorization is insufficient. Repository-mode default-branch/author filters and indefinite lifetime do not apply here. Do not change any existing repository-mode watch or its heartbeat to batch mode.

Read [$repair-pr](../../repair-pr/SKILL.md), its [shared coordination reference](../../repair-pr/references/stack-coordination.md), and [$manage-stacked-prs](../../manage-stacked-prs/SKILL.md). Retain the batch's validation policy for delegated repairs: skip manual app launches, real-environment reproduction, and validation screenshots; run required automated checks and disclose skipped validation. Preserve the repair comment policy. Never merge or enable auto-merge.

## Establish the batch watch

1. Recover the original human invocation, batch ID, durable absolute ledger path, host/repository, project ID, push remote, coordination root, stack IDs and catalog IDs, ordered layers/PR URLs, ready/publication evidence, and construction owners. Verify the recorded publication against authenticated GitHub and confirm the clean integration checkout was detached at its verified tip; do not adopt existing fixing PRs that the batch only reported. The complete target set is every recorded published PR from this batch, including upper layers. Do not filter by author or default base and do not search for additional PRs. A PR remains in the ledger after closure/merge or base retargeting; never create a replacement PR for it.
2. Verify the repository/project and actual `repair-pr` installation, its `manage-stacked-prs` dependency, helper and common-directory root, authenticated GitHub access, and scheduling/chat tools as in repository-mode preflight. Repair chats use `model: "gpt-6-luna"`, `thinking: "xhigh"`, and prompt exactly `$repair-pr <exact-pr-url>`. Do not substitute a model, a standalone automation, subagents, or local repairs. The common directory must match in every repair worktree. A readable skill in the coordinator is not sufficient proof of discovery in children.
3. Keep one maintenance record in the existing batch ledger and this coordinating chat. Add mode `batch`, implementation-ended flag, automation ID/state and uncertain outcomes, cadence, exact delegated PR identities/order, original authorization and comment scope, attempt history/creation IDs/actual chat IDs/worktrees, ownership/reservation/claimed tokens, final heads/alignment and thread outcomes, wait cursors, archived state, skipped validation, and blockers. Atomic helper state owns locks; the ledger owns human authorization and creation/repair history. Reconcile both on every continuation.
4. Discover existing automations through the tool's documented mechanism (`$CODEX_HOME/automations/*/automation.toml`) and match batch ID, this chat, repository, and ledger. Reuse the matching heartbeat. If another chat owns it, report that owner instead of registering a competing heartbeat. Reconcile overlapping repository watches and repair chats before assignment; use the shared whole-stack reservation so only one owner can dispatch. Do not widen an existing general watch's query to include the batch.
5. Register the first heartbeat when the first stack has passed complete publication verification and the helper's `ready` transition. Subsequent ready handoffs update the same ledger and watch; no new heartbeat is created. Preserve an existing or user-specified interval; default a new watch to five minutes. The construction subagent ceiling does not cap maintenance chats. Apply only user/app concurrency limits, plus the invariant of at most one preparing/running repair per stack. Distinct stacks dispatch in parallel.
6. Use `automation_update` to create/reuse one heartbeat in this coordinating chat with the saved prompt below, filling all placeholders. Preserve notification preferences and unrelated fields. Record and reconcile the actual registration result before dispatch. A creation failure leaves publication intact and maintenance reported inactive/uncertain; retry only after reconciling whether registration occurred. Immediately perform one bounded scan after successful registration, then return to implementation without waiting for repair completion.

Local maintenance requires the computer and Codex app to remain running. If no PRs were published, do not register a heartbeat. An interrupted or held stack remains construction-protected and is reported as a blocker; its visible partial PRs do not authorize repairs.

## Each bounded batch pass

1. Honor an explicit watch stop before any assignment. Record stopped state, deactivate the recorded heartbeat, and collect already-finished results without starting new repairs. Report uncertain deactivation. Stopping maintenance does not imply cancellation of running repairs or deletion of construction locks. Only an explicit human resume restarts a stopped watch.
2. Recover the ledger and helper `status`. Reconcile build owners, preparing/running/uncertain creations, reservations and claimed tokens, catalog recovery, prior pushes, thread outcomes, and other managers. Reuse shared result collection, corrected retry, comment, and archiving rules. Keep incomplete, failed, ambiguous and externally blocked repairs recorded; do not call an idle chat complete.
3. Reconcile newly recorded ready handoffs with complete remote publication evidence. Update the same delegated PR set from the ledger; this is inclusion of that batch's own outputs, not an issue rescan or authorization to adopt other PRs. Only stacks whose helper phase is `ready` can be assigned. Do not alter building or held stacks. A registry transaction/error or missing authorization/ledger data defers assignment instead of creating a fresh run.
4. Fetch a complete authenticated inventory for every currently recorded PR, including partial publications solely for status/termination accounting. Include open/closed/merged state, exact head repository/branch/SHA, current base branch/SHA, mergeability, current-head checks and latest attempts, and paginated relevant reviews/comments. Reconcile head/base changes during reads. Missing data is not a healthy result. Use the main skill's repair-signal assessment; pending checks, missing approval, or unknown mergeability alone do not trigger repair. Do not run the repository-mode default-branch filter in scanning, recovery, or dispatch.
5. Validate actual stack membership and current base chain, including GitHub retargeting after a parent merged. A legitimate base change does not exclude the recorded PR. Reconcile it under `manage-stacked-prs`; uncertain ancestry or concurrent membership changes block that stack rather than authorize a guessed replay. Closed/merged PRs receive no new repair and are never rewritten. Preserve original records; the stack's remaining open upper layers remain eligible when their current boundaries can be verified.
6. Prepare the coordination helper's `plan` inventory using these fresh reads, the implementation-ended flag, and all preparing/running/uncertain active stack IDs. Require `complete: true` for new assignments. Select the lowest open PR with a verified repair signal in each free ready stack; reuse prior-attempt evidence to avoid repeating an already handled problem and to correct an incomplete attempt. If a lower signaled repair is blocked, do not skip it to mutate an upper layer; continue other stacks. External-log or missing-decision blockers remain associated with that stack, not a retry loop.
7. Immediately before each dispatch, re-read the PR's open state, head/base, signal, actual stack and other owners. Reserve the whole stack with `acquire --mode reserved`; a stale plan does not confer ownership. Persist the attempt and returned token before creating the dedicated worktree chat. Record the actual creation response/IDs immediately; the assigned child verifies its creation identity in the ledger before claiming the reservation. Leave uncertain creations reserved. A definite rejected creation can release its reservation after reconciliation. Never create two children for one reservation or allow another watcher to dispatch into it. Preserve the exact one-line repair prompt.
8. Collect bounded `wait_threads` snapshots and record target repairs separately from upper-only replay/alignment, final remote heads, validation, push/thread outcomes, and archive state. Require alignment verification, not only a target push. After a lower repair finishes, fetch new head/base/check/review state for the next candidate; discard earlier upper-layer signals that disappeared or became obsolete. Do not dispatch the next same-stack repair until ownership and effects are reconciled. Continue other free stacks without waiting for all children.
9. Re-evaluate termination using current complete terminal PR states. End automatically only when the ledger says implementation ended, every published PR is closed/merged, and no preparing/running/uncertain repairs or unreconciled/incomplete stack ownership remains. Record completion and deactivate this batch's heartbeat; verify the tool result. An implementation still running, missing inventory, empty interim PR list, healthy open PRs, or an interrupted build is not completion. Report incomplete construction or unresolved ownership requiring action; never release it to make shutdown succeed.

One pass never waits for CI/reviews to settle or repeatedly retries the same failed command. Reuse the main skill's corrected automatic recovery: a remaining verified repair signal may justify a new attempt after reconciling the previous effects and correcting the failure cause. This permission applies only to the fixed delegated PR set. Report failures and required action, and stay quiet while state is unchanged or non-actionable.
